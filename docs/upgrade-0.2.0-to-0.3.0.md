# 0.2.0 → 0.3.0 下游对接说明

**给下游宿主（V-Trim）**。产物：`dhampir-0.3.0-win32-x64.zip`。

## 0. 一句话

契约号未动（`project_schema = 1`、`host_api = 6`），不改代码即可用；新增可选字段 `source.source_rate`（画面 / 音轨变速），不写就与 0.2.0 逐字节相同（见 §5）。

## 1. 新增字段：`source.source_rate`

`{"source": {"asset_id": "clip", "source_in": 60, "source_rate": 2.0}}`，等价 ffmpeg 的 `setpts=PTS/2`：`rate=2.0` 两倍快放，`0.5` 半速慢放。

| 字段 | 含义 |
|---|---|
| `end - start` | **输出帧数**（占多长输出时间） |
| `source_rate` | 每输出 1 帧消耗几个源帧（缺省 `1.0` = 原速） |
| 消耗的源帧 | `(end - start) × source_rate`，从 `source_in` 起算 |

## 2. 音轨也一起变速了（不是只改画面）

读 `output_samples × rate` 个采样点再用 `atempo` 压回来，两头一凑输出时长不变；`atempo` 不变调；`rate < 0.5` 自动拆多级（`0.25 = 0.5 × 0.5`）；`rate > 100` 明确报错。

## 3. ⚠️ 请改掉亮度验收的口径 —— 你们上一轮的结论是错的

### 3.1 你们报的

现状 out 0..29 → YAVG `99 → 147`；支持后 `100 → 198`。对比本身没错，两组数字都量错了量纲。

### 3.2 真相

本仓解码带 `-vf scale=out_color_matrix=bt709`，源 Y（tv 16..235）转成出片 R（full 0..255）：`R = (Y − 16) × 255 / 219`。`(100 − 16) × 255 / 219 = 97.8` ⇒ 出片 **97** 不是漂移；`147` 对应源 Y ≈ 148。

### 3.3 对齐口径后：30/30 帧精确

`out[i] == ( src[60 + 2i].Y − 16 ) × 255 / 219`（`source_in=60`、`rate=2.0`、out 30 帧，30/30 吻合；`rate=1.0` 同样精确）。

### 3.4 一个容易骗过人的地方

`R − Y` 随亮度线性增大（低处 −3、高处 +13），像时间漂移；真帧漂移是阶梯，不是线性。误差随被测量线性增长时，先怀疑量纲。

### 3.5 建议你们改成

`const expect = (srcY - 16) * 255 / 219;` 换算后再比，或干脆比结构（帧数、相对变化率、首末落点），不比绝对亮度。

## 4. 你要改什么

### 4.1 必须做

换产物为 `dhampir-0.3.0-win32-x64.zip`（结构与 0.2.0 完全一致）；改亮度验收口径（见 §3，唯一要动脑子的地方）。

### 4.2 不用做

改契约校验（`project_schema = 1` 没动）、改 wasm 导出调用（`host_api = 6` 没动）、改产物路径解析（`preview/` + `bin/` + `VERSION`）、重新调字幕像素、给老工程加字段。

### 4.3 想用变速时才做

在 `source` 里加 `source_rate`。`rate <= 0` / `NaN` / `inf` ⇒ `probe` 报 `source_rate_invalid`；`rate > 100` 报错；`0 < rate < 0.5` 允许（自动拆多级 `atempo`）。故意不兜底成 1.0。
