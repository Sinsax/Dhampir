# 底座缺陷：`outline = true` 时字幕渲染成一整块实心糊团

**发现日期**：2026-10-13（P4 逐字对拍施工期间，取真机像素证据时偶然撞见）
**严重程度**：高 —— 凡是开了描边的工程，**字幕完全不可读**
**与逐字功能的关系**：**无关**。它在本会话的改动之前就存在，且老路（`paint_parts`，
不含任何逐字代码）与逐字路（`paint_per_char`）产出**逐字节相同**的糊团。
**本会话是否动过相关文件**：没有（`git log -- crates/dhampir-worker/src/text_raster.rs` 最近
三次提交都不是本会话的）。

---

## 一句话

底座的 `text_raster.rs` 在 `outline = true` 时，把字画成一整块**实心糊团**
（覆盖率密度 0.92），而不是"字 + 一圈描边"；`outline = false` 时同一句话完全正常
（密度 0.36）。`lines_drawn = 1`、`failed = false`、`issues` 为空 —— **没有任何报错**。

## 最小复现（已实测，与本仓既有测试夹具无关）

固定工程：1080p、`font_ratio = 0.08`、`font_family = "Default"`（字体目录里放
`Default.ttf` = `C:\Windows\Fonts\simhei.ttf`）、文本「逐字散开测试」、`stroke_ratio = 0.005555…`
（⇒ `stroke_px = 6`）。**只改 `outline`**：

```
$ dhampir frame --project p.json --frame 10 --out out --font-dir fonts
```

| `outline` | `font_weight` | 墨数 | 包围盒 | **覆盖率密度** | 观感 |
|---|---|---|---|---|---|
| `false` | 400 | 15504 | 508×84 | **0.363** | 清晰的「逐字散开测试」 |
| `true`  | 400 | 47075 | 568×90 | **0.921** | **一整块实心糊团** |
| `false` | 700 | 15504 | 508×84 | 0.363 | 清晰 |
| `true`  | 700 | 47075 | 568×90 | 0.921 | 一整块实心糊团 |

⇒ **`font_weight` 无影响**（400 与 700 逐值相同）；**`outline` 是唯一开关**。
密度 `0.921` ≈ "整块填满"，而真实字形（汉字笔画）应当落在 `0.3–0.45`。

## 为什么"覆盖率密度"是这里的判据

不能只看"有没有墨" —— 糊团**也有墨**，而且墨更多。必须看
**墨数 ÷ 包围盒面积**：真实字形有大量笔画间空白，糊团没有。
⚠️ 这也正是我在 P4 判据上栽过一次的形状：只量"包围盒变宽了"会把
"整行平移"误判成"逐字散开"。**量一个总量，必须同时量它的分布。**

## 已排除的假设（逐条实测过，别再重复）

| 假设 | 怎么排除的 |
|---|---|
| 逐字功能（我的 P3 改动）造成的 | 关掉 `anim`/`per_char` 的老路产出**逐字节相同**的图 |
| 字体文件不对 | `simhei.ttf`（真 TTF、全中文）与 `msyh.ttc` 都试过；底座自带的 `真起_ffmpeg_画出一行中文字` 单测**通过** |
| 字库缺中文字形（`.notdef` 方框） | 方框是**规则空心矩形**，而这里是**不规则的实心块**，且 `outline=false` 时同一字体画出正确的字 |
| `--font-dir` 指错 / libass 静默回退 ArialMT | 回退的表现是"字体不太对"，字形结构仍在；这里是**结构整个消失** |
| libass 的 `PlayRes` 缩放 | 直接量过：`FontSize` 按底座的 `ass_font_size` 公式（`font_px × 1.25 × 288/高`）给值时，ffmpeg 单独渲染**清晰** |
| 描边宽度太大（`stroke_px` 过大） | `stroke_px = 6`（1080p、`font_ratio=0.08`）是**合理**宽度；且这条路上 `ass_outline_px` 是**恒等函数**，没有放大 |
| 字体路径含非 ASCII | 该路径已有 `ascii_font_path` 处理，且有单测钉住 |

## 尚未定位的点（下一轮从这里接）

已确认**现象**与**唯一开关**，但还没走到根因。已知的边界：

* `coverage_from_libass`（`text_raster.rs:1151`）把 libass 输出的 **RGB 均值**当覆盖度。
  它的文档写着"libass 的 alpha 恒为 0、颜色提前合成进 RGB"。
  ⚠️ **开描边时 libass 会把描边色也合成进 RGB** —— 而这里 `OutlineColour` 写的是
  `WHITE_INK`，若描边被画成**不透明白**并覆盖整行，`mean` 就处处接近 255
  ⇒ 覆盖度处处为 1 ⇒ **整块实心**。这与观察到的密度 0.921 高度吻合。
  下一个该看的就是：`Outline=6,OutlineColour=&H00FFFFFF` 这一串在 libass 里
  到底画出了什么（把 `run_ffmpeg` 的滤镜串打出来，用同一个串手工跑一次 ffmpeg 对比）。
* `style` 串里**没有 `PlayResX/PlayResY`**（`LIBASS_PLAY_RES_Y` 的注释解释了为什么不写、
  以及它用 `FontSize` 补偿）。这条本身**不是**本缺陷的成因（单独验过），
  但它意味着"描边宽度"也在那个 288 高的虚拟画布上被缩放 —— 值得一并核。
