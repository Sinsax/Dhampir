# 文字动效的逐帧通道 —— 宿主接入指南（T1 弹入 / T3 强调 / T4 抖动）

**适用产物**：`dhampir-0.3.0+`（`project_schema = 1`、`host_api = 6`）。

这份文件只回答一件事：**YekiTrim（宿主）要开"字幕弹入 / 逐条强调 / 抖动"，
该往工程 JSON 里写哪些键、每个值的口径是什么、不写会怎样。**
设计理由在 [../plan/](../plan/)、形状权威在 [host-api.md](host-api.md)。

---

## 一、这一版变了什么（一句话）

**文字的"逐帧动效"从宿主搬进了底座**：以前宿主自己算每帧的缩放/位移再喂给渲染，
现在宿主只在工程里写**动效参数**，底座按帧号算出来 —— 于是**预览（浏览器）
与成片（CLI）用的是同一份计算**，两边不会各算各的。

对宿主的实际意义：

* 宿主**不需要**逐帧算 `scale`/`offset` 了，写 6 个静态参数即可；
* 新增字段**全部可选**，老工程**一个键都不多**（见 §四）。

### 兼容性

| 面 | 变没变 |
|---|---|
| 工程文件形状（`project_schema = 1`） | 老工程**照读，一个键都不多**（不写就不出现） |
| `dhampir_host_api_version` | **6（不变）** —— 这次是**加字段**，导出面形状没动 |
| 既有字段 | **全都不变** |

**判据**：只写老字段的工程，对着新产物**出片逐字节相同** ——
`text_enter::全部缺省时逐字节等于老工程` 就是这条的执行处。

## 二、字段一览（这是契约）

六个键都挂在**字幕轨**的 `subtitle` 对象上（与 `font_ratio` / `color` 同级）。
**全部可选**，类型是 `Option`：**不写 = 关**，写 = 写的那个值。

| 键 | 类型 | 单位 | 默认（不写时） | 干什么 |
|---|---|---|---|---|
| `scale_in_from` | `f32` | 倍率 | `1.0` | 弹入**起点**缩放。参照 `0.7` |
| `scale_in_peak` | `f32` | 倍率 | `1.0` | 弹入曲线的**终点**倍率。参照 `1.15`（⚠️ 不是实际峰值，见 §三） |
| `scale_in_ms` | `u64` | 毫秒 | `0` | 弹入窗口时长。**`0` = 关**（唯一决定开不开的键） |
| `shake_px` | `f32` | **文档像素** | `0.0` | 抖动幅度。**`0` = 关** |
| `shake_hz` | `f32` | Hz | `18.0` | 抖动基频。**`<= 0` 视为关** |
| `shake_phase` | `f32` | 弧度 | `0.0` | 抖动相位。同屏多条给**不同值**才能各自晃 |

> ⚠️ **单位是文档像素，不是目标像素** —— 与 `rise_in_px` / `transform.x/y` 同一套。
> 于是预览的小画布与成片的 1080p 落到同一个比例。

### 参照值（想要"参照实现 那个观感"就写这一组）

```json
{
  "subtitle": {
    "font_ratio": 0.055,
    "scale_in_from": 0.7,
    "scale_in_peak": 1.15,
    "scale_in_ms": 180,
    "shake_px": 14.0,
    "shake_hz": 18.0,
    "shake_phase": 0.0
  }
}
```

## 三、⚠️ 三条容易踩的口径

### 3.1 `scale_in_peak` 是**曲线端点**，不是实际峰值

两者**不相等**，这是最容易误读的一条：

```text
scale(p) = from + (peak − from) × back_out3(p)
back_out3 在中点 p=0.5 冲到 1.25（s=3 的固有峰值）
⇒ 实际最大 = 0.7 + 0.45 × 1.25 = 1.2625   ← **不是** 1.15
```

**实测印证**：`text_enter::t1_弹入逐帧先缩后过冲再回落` 里逐帧量外接框，
峰值帧宽比约 **1.245**（1.2625 取整到像素）。想改"过冲多少"要同时动两个端点。

### 3.2 曲线用的是 `s = 3`，**不是**经典的 `1.70158`

底座的 `easing::EasingForm::BackOut` 系数**写死 1.70158**（峰值 1.10）。
文字弹入用的是**参照实现 的 `s = 3`**（峰值 1.25），所以曲线在
`dhampir_timeline::text_motion::back_out3` 里**单独算**。
宿主侧若自己实现曲线（YekiTrim 的 `backOut3`），**必须与它逐值一致** ——
不一致的症状是"预览弹的幅度与成片不同"，而两边各自看都正常。

### 3.3 抖动是**纯 `t` 的函数**，没有累积状态

`text_shake_px(t, …)` 只吃当前时刻。这是刻意的：**预览是 `seek` 的、成片是顺序的** ——
靠"上一帧在哪"累加的话，两条路会分叉。宿主不需要、也**不应该**自己推进抖动状态。

相位表（两个正弦叠加，非整数倍频率才是手抖而不是机械抖）：

```text
dx = px × ( 0.62·sin(2π·hz·t      + φ)   + 0.38·sin(2π·hz·2.7·t + φ·1.9) )
dy = px × ( 0.62·sin(2π·hz·1.3·t  + φ+1.1) + 0.38·sin(2π·hz·3.1·t + φ·0.6+2.3) )
```

**`shake_phase` 必须逐条不同**：同屏两条相位相同会**整体同拍**地一起晃，
那不是"两条在抖"，是"整块字在抖"，看着像画面在抖。

### 3.4 T3 强调：`cue.scale` **不在工程 JSON 里**

强调放大是**逐条**的，挂在字幕**条目**上而不是轨道样式上。但它
**没有"从工程文件读"这条路** —— 它是**宿主在运行时给**的逐条事实：

| 位置 | 类型 | 说明 |
|---|---|---|
| 字幕轨 `subtitle.*` | 上面那 6 个键 | 轨道级，工程 JSON 里写 |
| 条目 `Cue.scale` | `Option<f32>`，`None` = 1.0 | **逐条**，宿主在 `SubtitleTable` 里设 |

⇒ 往工程 JSON 的 `layers[].scale` 里写**不会被读到**（会报未知键或被忽略）。
宿主要走 `dhampir_timeline::subtitle::Cue { scale: Some(1.3), .. }` 那条路。

**三个缩放是相乘的，不是覆盖**：

```text
最终字号倍率 = line.scale × enter_scale × cue.scale
               └ 装不下的整体缩字  └ T1 弹入   └ T3 强调
```

写成覆盖的话，"弹入还没结束就命中高亮"会**突然跳一下**（从 0.7 跳到 1.3）。

## 四、存量零回归：**一个键都不多**

六个键都带 `#[serde(default, skip_serializing_if = "Option::is_none")]`：

* **不写** ⇒ 反序列化成 `None` ⇒ 求值是**单位变换**（缩放恒 1.0、抖动恒 0）⇒
  出片**逐字节相同**；**重写工程也不会多出这些键**；
* **写** ⇒ 就是写的那个值，**哪怕它恰好等于默认值**（`"scale_in_from": 1.0` 留得住）。

> 这条为什么用 `Option` 而不是裸 `f32` + "等于默认就不写"：
> 后者会把**用户显式写的 `1.0`** 静默吃掉 —— 读回来仍是 1.0、渲染也一样，
> 所以**永远不会有症状**，但用户的显式意图没了。而"显式写了却读不回来"
> 是本仓最恨的那类静默。

**三层判据都在**（缺一层就有漏法）：

| 层 | 判据 | 抓什么 |
|---|---|---|
| JSON 键 | `layer::v2_tests::没写过阴影的样式重写出来一个字节都不多` | 多写了键 |
| 求值 | `text_motion::默认样式求值出来是单位变换` | 默认值走岔 |
| 出片 | `text_enter::全部缺省时逐字节等于老工程` | 像素变了 |

## 五、宿主接入清单（YekiTrim 侧要做的）

1. **写 6 个键**进字幕轨的 `subtitle`（参照值见 §二）；
2. **删掉**宿主侧自己算的逐帧缩放/位移 —— 底座已经算了，
   两边都算会**叠加两次**（症状：动效幅度是两倍）；
3. **强调放大**走 `Cue.scale`（§3.4），不要往 `layers[].scale` 写；
4. **抖动相位逐条错开**（按条目序号×一个常数即可）；
5. 判据：只写老字段时**出片逐字节相同**；写新字段时
   预览与成片的**逐帧外接框/质心**要一致。

## 六、这次顺手修掉的一个**既有** bug（宿主会感知到）

**"逐条缩放"在本仓从来没真正生效过。** 渲染侧的字号来自
`place_line(rect, target, style.font_ratio)` —— **轨道级**的 `font_ratio`，
而逐条的 `scale` 只落在**描边宽度**上（`stroke_px * scale`）。

⇒ 影响：`line.scale`（装不下时的整体缩字）与新的 T1/T3 **都不动字号**。
本仓已修：求值层现在给 `font_ratio` 乘上逐条缩放，且
**wasm 与 CLI 两条路都读同一个 `font_ratio`**（此前 wasm 读条目、CLI 读轨道，
两条路本来就不一致）。

**判据**：`text_enter::t1_弹入逐帧先缩后过冲再回落` ——
出片逐帧量文字外接框，先 `<1`、再 `>1`、后回 `1.0`。
