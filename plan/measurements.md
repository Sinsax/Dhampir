# P5 性能测量：三个数与其量纲

> plan 的 P5.2 判据是「**三个数落盘**，据实定队列并发度」。
> 这份文件就是那次落盘。**每个数都带它的量纲限制** ——
> 一个没有边界的数字比没有数字更危险，因为它会被当成结论用。

测量脚本（都可重跑）：

| 脚本 | 量什么 |
|---|---|
| `scripts/measure-render.mjs` | 渲染吞吐 |
| `scripts/measure-concurrency.mjs` | GPU 并发 |
| `scripts/measure-asset-io.mjs` | 素材取用的 IO 与延迟 |
| `scripts/measure-export.mjs` | **完整出片**（第五项，P6 补） |
| `scripts/measure-raster.mjs` | **单条字幕的栅格化**（第六项，T2 补） |
| `cargo run -p dhampir-worker --example rewind_census -- <工程>...` | **解码回退的分布与池子读数**（第七项，T5 补；纯计算，不要 GPU/ffmpeg） |
| `cargo run -p dhampir-worker --example decode_cost -- <工程>...` | **解码这一段的代价与并发**（7.4，T5 补；要真 GPU 与 ffmpeg） |

## 一、渲染吞吐

    30 帧：1221 ms
   150 帧：2823 ms
   边际每帧：13.35 ms
   外推到 1800 帧（60 秒 @30fps）的渲染分量：约 24.0 秒

**方法**：测两个样本量、用差值算**边际**每帧成本。
直接拿总时间除帧数会把进程启动的开销摊进每帧里，得出「每帧很贵」的假结论。

**量纲限制**：worker 用的是 core 的**合成源**，不解码任何视频。
所以这 24.0 秒**不是**「1 分钟素材要多久」，只是那个答案的**渲染分量**。

**一次值得记的过程**：第一次用 4/16 帧，得到 **-8.62 ms/帧**（16 帧比 4 帧还快）；
同一对样本第二次跑得到 **+14.89** —— **符号都反了**。
两次合起来才是结论：**4/16 分辨不出信号**。
脚本当时把负数当结果打印了，那是它的缺陷：**负的每帧成本不是「很快」，是「测不出来」**。
已加判据：边际每帧非正数时明说「测不出来」并退出码 1。

## 二、GPU 并发

    单跑（60 帧）：1717 ms
   并发 2 个（各 60 帧）：整批 1982 ms
   比值 1.15

**方法**：分别测「单跑」与「K 个同时启动」的墙钟，看比值。
~1.0 是完全并行；~K 是完全串行（加并发只是排队）。

**量纲限制（这一项最强）**：负载只有 60 帧 x 320x180，GPU 远没吃满；
而且每次约 1 秒的**进程启动 + wgpu 初始化是在并行里同时付掉的**，它把比值压向 1.0。
所以 1.15 里有相当一部分是「**启动并行**」而不是「渲染并行」。

**诚实的结论只有一句**：在这个量级下 GPU 有余量。
要回答「1080p 出片能并发几个」，需要把测量跑在真实输出尺寸上 ——
而那要求 `render_project` 支持尺寸参数（与 G5 的输入对齐是同一个待办）。

## 三、素材取用的 IO 与延迟

    整段下载（6.20 MB）10 次：平均 16.1 ms/次 -> 385 MB/s
    单个分片 Range 请求（586 KB）20 次：p50 2.1 ms，p95 3.6 ms，全部 206

**量纲限制**：走 loopback（127.0.0.1），所以它是**上限**，不是真实网络的数字；
不含 RTT、丢包与带宽限制。

**它带来的一个实际结论**：loopback 下取一个 GOP **几乎免费**（p50 2.1 ms）。
也就是说此前反复讨论的「拖动延迟」担忧**完全在真实网络那一侧，不在服务端**。
服务端素材取用不是瓶颈 —— 这件事现在有数字了，以前只有推测。

## 据实定队列并发度

三个数**都不足以**定一个数字出来，理由如下：

| 想要的 | 缺什么 |
|---|---|
| 出片任务能并发几个 | 并发测量跑在 320x180 上，**真实尺寸下的数字没有**；且不含解码 |
| 单机出片吞吐（帧/秒） | 渲染分量有（13.35 ms/帧），**解码分量没有** |
| 能撑多少编辑用户 | loopback 上限有，**真实网络没有** |

**所以这里不给一个并发度数字。** 给了就是拿带边界的数当结论用 ——
而那正是这份文件开头说的、比没有数字更危险的事。

能给的只有一条**方向性**判断，且标明它是方向性的：

> 出片侧的并发**必须由队列限流**（GPU 只有一个 device，并发只会互相拖慢）；
> 编辑侧（素材取用）在服务端**不是瓶颈**，瓶颈在真实网络。

## 五、完整出片吞吐（P6 补测）

前四个数共同的空缺是**解码**。P6 把多源顺序解码接进渲染之后，这个空缺补上了：

| 用例 | 帧数 | 每帧 ms（中位） | 最小 | 最大 | 端到端 ms |
|---|---|---|---|---|---|
| 640x360  / 90 帧 | 90 | 14.56 | 14.42 | 14.76 | 1310 |
| 1920x1080 / 30 帧 | 30 | 22.50 | 22.10 | 22.60 | 675 |

三次重复取中位；脚本 `scripts/measure-export.mjs`。

**这一行是「用户按下导出之后要等多久」的那一类数**：它包含
逐源 ffmpeg 顺序解码 -> 上传 -> 求值 -> 合成 -> 读回 -> 编码成 mp4 的全过程。

**量纲限制（别当容量数）**：

- 样本工程的四个 asset **指向同一份文件**。四路解码器读同一个文件，页缓存会帮忙 ——
  换成四份不同素材只会更慢，所以这是**下界**（**T5 已补测，见 7.4**：同一条时间线
  换成四份不同文件是 56.96 ms/帧，同一份文件是 40.90 ms/帧）；
- 每帧**同步等待读回**，不是流水线吞吐。真实出片可以让读回与编码重叠，边际成本会更低；
- 单机单卡（本机 Windows / 一块 NVIDIA）。别的机器别照搬；
- 尺寸影响很大：读回与编码都跟着尺寸走（14.56 -> 22.50 ms 里有相当一部分是它）。

**它带来的一条实际结论**：640x360 的 90 帧工程（3 秒成片）端到端约 **1.3 秒**，
也就是说**本地出片已经比"等它"更快**。1080p 下 22.5 ms/帧意味着 1 分钟素材约 40 秒 ——
仍然远快于实时，所以单机模式下的"导出"不像传统剪辑软件那样是个要泡咖啡的等待。

## 六、单条字幕的栅格化成本（T2 补测）

| 目标 | 字号 px | 位图 | 每张 MB | 冷中位 ms | 冷最小 | 冷最大 | 热 ns/op | 1 冷 + 89 热 ms |
|---|---|---|---|---|---|---|---|---|
| 1920x1080 | 59 | 1920x109 | 0.80 | 55.7 | 52.7 | 61.9 | 490 ~ 516 | 55.8 |
| 640x360 | 20 | 640x36 | 0.09 | 50.0 | 48.4 | 51.7 | 490 ~ 493 | 50.1 |

三次重复；脚本 `scripts/measure-raster.mjs`（带 `--self-test`，4 条断言）。

**方法**：把两段**分开**量，因为它们的量纲完全不同 ——

* **冷**（第一次见到这一行）：写临时文本文件 + 起一次 ffmpeg + 读回字节 + 染色；
* **热**（命中缓存）：一次哈希查找加一次 `Rc` 克隆。

「一条字幕在 90 帧（3 秒 @30fps）上出现」的栅格化成本由这两段合成：**1 冷 + 89 热**。
拿冷路径乘帧数会得出「一行字幕在 3 秒里要 4.5 秒」这种自相矛盾的数 ——
那是**没有缓存**的世界，而缓存不是优化、是可行性。

**量纲限制**：

- 冷的 ~50 ms **几乎全是 ffmpeg 的进程启动**：640x360 的位图字节量只有 1080p 的九分之一
  （0.09 MB 对 0.80 MB），耗时只差 6 ms。所以它是一条**每次进程**的固定成本，
  几乎不随输出尺寸变 —— 这恰恰解释了缓存为什么必须存在。
- 本仓的 Rust 部分是 debug 构建（`cargo run` 的默认档），ffmpeg 是 release 的外部程序。
- 位图宽度取**整条目标宽**，所以 1080p 一张 0.80 MB —— 冷路径读的就是这个字节量，
  **不是**这一行的墨迹量。
- 取样行**不经共享布局的换行**（整行直接喂给 drawtext）：长混排行在两种尺寸下都碰边
  （`ink_touches_edge`）。那是「模型字宽 vs 真字宽」的差，**不是**产品路径的结论 ——
  产品路径先换行、再逐行画。
- 单机单字体（msyh.ttc）。换字体、换机器别照搬。

**它带来的一条实际结论**：一行字幕上屏的栅格化成本约 **56 ms**（1080p，含进程启动），
而命中缓存只要 **0.5 µs** —— 也就是说代价是「**每行一次进程**」，
与这一行在几帧上出现、出现在哪几帧都无关。

**一次值得记的过程**：第一次真跑这个测量就红了 —— 取样行里有一行带 `%`
（`数字 100 % 号`），ffmpeg 报 `Stray % near ' 号'`。原因是 `drawtext` 会对**文本内容**
做展开（`%{pts}`、`%{n}`、strftime 那一套），而文本是用户写的：
用户打个百分号，整条字幕就画不出来；`%{n}` 还会被**悄悄**换成帧号。
修法是 `expansion=none`（探针实测：默认档那一行 EXIT 非 0，关掉展开后同一行正常出图），
并补了一条**真起 ffmpeg 的反向用例** —— 把 `expansion=none` 换回默认档，这条就会红（验过）。
这件事值一句话：**测量夹具不是文档，它是会被真跑的代码**，所以它撞得出产品缺陷。

## 七、解码回退、纹理池与并发（T5）

T5.1 的规矩是「**没有数字就不许决定**」：先量回退有多常见，再决定做有界池子
还是按源内顺序重排渲染。这一节就是那次落盘。

### 7.1 回退有多常见、退多远

`cargo run -p dhampir-worker --example rewind_census -- <工程文件>...`（T5.1 的工具）。

它**不碰 GPU、不碰 ffmpeg**：取帧顺序从**求值层**摊出来（走的正是渲染器真会请求的那条路），
池子行为跑的是**产品同一段状态机**（`PoolCursor`）。所以下面这些数描述的是产品，
不是"另一种实现"。**回退的"距离" = 这次要的源内帧比这个源此前要过的最大帧号小多少。**

| 工程 | 帧 | 请求 | 不同源内帧 | 回退次数 | 回退占比 | 距离 p50 | p90 | 最大 |
|---|---|---|---|---|---|---|---|---|
| `sample-project`（顺序引用） | 90 | 140 | 130 | 0 | 0% | – | – | – |
| `rewind-project`（同一素材三段倒放） | 90 | 90 | 90 | 60 | 67% | 120 | 166 | 178 |
| `pip-project`（同一素材画中画，相距 100 帧） | 30 | 60 | 60 | 29 | 48% | 98 | 98 | 98 |
| **合计** | | **290** | | **89** | **30.7%** | **98** | **160** | **178** |

**据实得到的两条**：

1. 回退**很常见**（这份样本里 30.7% 的请求是回退），而且**退得不浅**（中位 98 帧）；
2. 于是**「按源内顺序重排渲染」这条路被否掉**了。它会打乱输出帧的访问顺序，
   而这一段的判据是**逐像素一致** —— 重排等于把"同一帧的结果"变成两件事。
   选的是「**有界池子 + 装不下就重启解码器从 0 再读**」。

### 7.2 池子要多大

**留几帧**由「这个源上还有几个没轮到它的请求」决定，**不是**由回退距离决定 ——
这是量出来才看清的一条。`倍数` = 读了多少源帧 / 这个工程有多少个不同的源内帧。

| 槽数 | `rewind-project` 读/重启/命中/倍数 | `pip-project` 读/重启/命中/倍数 |
|---|---|---|
| 1 | 355 / 2 / 1 / 3.94 | 3745 / 28 / 1 / 62.42 |
| 8 | 341 / 2 / 8 / 3.79 | 1771 / 14 / 15 / 29.52 |
| 16 | 325 / 2 / 16 / 3.61 | 387 / 2 / 27 / 6.45 |
| 32 | 234 / 1 / 32 / 2.60 | **159 / 0 / 29 / 2.65** |
| 64 | **179 / 0 / 60 / 1.99** | 159 / 0 / 29 / 2.65 |

`sample-project`（顺序引用）在**所有**槽数下都是 `271 / 0 / 10 / 2.08` ——
**顺序出片完全不受池子大小影响**。这是"池子没有把常见路径拖慢"的证据。

**两个常数就是这么反推出来的**（`pipeline.rs` 的 `POOL_BYTES_PER_SOURCE` / `POOL_SLOTS_MAX`）：

- 要覆盖**画中画那种形态**（同素材两处相距很远）最多要留住 **29 帧**；默认导出尺寸
  1080p 一帧 8.29 MB，`29 x 8.29 MB = 240 MB` -> 留余量取 **256 MiB**，
  1080p 下正好 **32 槽**（上表那一格正是重启归零、读帧量 6.18x -> 2.65x 的地方）；
- **不去**覆盖倒放那种形态（60 帧 -> 498 MB/源、四源 2 GB 天花板）：为它多花的钱只买到
  2.60x -> 1.99x，不值。改成把帧数**封在 64**（360p 按字节算会给到 291 帧，不封就失控）。

### 7.3 池子的账 == 产品的账（真机可对账）

`cargo test -p dhampir-worker --test rewind -- --ignored --test-threads=1 -- --nocapture`

| 工程 | 帧 | 解码器 | 命中 | 向前 | 重启 | 读源帧 |
|---|---|---|---|---|---|---|
| `rewind-project` | 90 | 1 | 32 | 57 | **1** | 234 |
| `rewind-sequential`（对照） | 90 | 3 | 0 | 90 | 0 | 357 |
| `pip-project` | 30 | 1 | 29 | 31 | 0 | 159 |
| `pip-sequential`（对照） | 30 | 2 | 0 | 60 | 0 | 218 |

**这张表与 7.2 的 32 槽那一行一位不差**（234/1/32 与 159/0/29）。这就是
"量化脚本与产品共用一段规则"的兑现方式 —— 不是自称同源，而是**对上了**。

顺带两个可以直读的结论：

- 倒放工程**一路源**读 234 帧，比"拆成三路源"的 357 帧**更少** ——
  池子接住回退比多开两个解码器便宜；
- 画中画工程**一路源**读 159 帧，比两路源的 218 帧少 —— 这是"按 (源, 源内帧) 键复用"
  买来的。

### 7.4 解码并发数与它的代价（T5.3）

**并发数是 1。** 取帧是一条**同步循环**：每个输出帧里按层序依次调
`texture_for`（`crates/dhampir-core/src/render/timeline.rs:362`），每一次都是一次**阻塞**的
`read_exact`（`crates/dhampir-worker/src/pipeline.rs:649`）。所以**同时最多一个源在解码**，
哪怕开着 N 路解码器 —— 7.3 表里那一列是"**开着几路**"，不是并行度。

代价是两项：**（进程与内存）** N 路 = N 个 ffmpeg 子进程 + N 个池子上限（256 MiB/源）；
**（不重叠）** 解码不与合成/读回重叠，所以"每个源帧读"的墙钟是**串行相加**的。

实测（`cargo run -p dhampir-worker --example decode_cost -- <工程>...`，三次取中位）：

| 工程 | 帧 | 解码器 | 读源帧 | 墙钟 ms | 每帧 ms | 其中 PNG 编码 | 剔掉 PNG 每帧 | 每源帧读 | 读进多少字节 |
|---|---|---|---|---|---|---|---|---|---|
| `sample-project`（4 个 asset -> **同一份文件**） | 90 | 4 | 271 | 6282 | 69.80 | 30.04 | **40.90** | 13.58 | 2.25 GB |
| `four-asset-project`（**四份不同文件**，含一份 4K） | 90 | 4 | 271 | 8220 | 91.34 | 35.41 | **56.96** | 18.92 | 3.60 GB |
| `rewind-project`（一份素材、1 次重启） | 90 | 1 | 234 | 4648 | 51.65 | 26.22 | **25.19** | 9.69 | 1.94 GB |

**D11 说的那条"下界"现在有数了**：同一条时间线、同样 271 次读，
把素材从"四份指向同一文件"换成"**四份不同文件**"之后，每帧 **40.9 -> 57.0 ms（+39%）**。

不过换成**按读进来的字节**算就不悬殊了：`sample` 搬 2.25 GB / 3680 ms = **1.64 ms/MB**，
`four-asset` 搬 3.60 GB / 5126 ms = **1.42 ms/MB** —— **反过来了**。
也就是说墙钟差主要来自**多搬了 1.6 倍字节**（其中一份是 4K，33.2 MB/帧），
**不是**"页缓存不帮忙了"。这条比原始数字有用：它说明**源素材的像素字节量**才是这一段的价钱，
换成真实工程（多份不同素材）不会出现"比下界差好几倍"这种事。

**一张表里没有的、必须说清楚的事**：这张表**换了一把尺子**（PNG sink、且计时**含 GPU 初始化**），
所以**不能**与第五项的 14.56 ms/帧 直接比。两者差了 2.6 倍，而**这次会话里对不上账** ——
出片那条路要起编码器，而 agent 会话起不了（坑 19，见 next-steps.md）。
**留一条明确的待办**：在普通终端里重跑 `node scripts/measure-export.mjs`
（同一个工程、同一段帧 0..89、同一尺寸），若仍是 ~14.5 ms/帧，说明 PNG 那条路真的更慢、值得追；
若变成 ~40 ms/帧，说明第五项那个数已经过期。**在有人重跑之前，两边的数都别当结论用。**

**量纲限制**：

- 本仓 Rust 侧是 **debug** 构建。PNG 编码在 debug 下的 deflate 很贵（表中单列），
  所以看解码成本要看"剔掉 PNG"那一列；
- 「每源帧读」是**摊**出来的（含上传、合成、读回），**不是**解码净耗时；
- 单机单卡（本机 Windows / 一块 NVIDIA）；别的机器别照搬；
- **没有**把"四份指向同一文件"与"四份文件本身大小不同"分开 —— 要分开得用同一份文件的
  四个副本（见"未做"）。所以这条 +39% 是**"页缓存"与"字节量"两个原因合起来**的效果；
- **为什么不顺手把解码并发化**：池子已经把回退变成命中（7.2 里读帧量 2.08x~2.65x），
  而这一段每帧 25~57 ms、整段 4.6~8.2 s；**没有量到它是瓶颈**，所以这一轮不动它 ——
  并发化的代价（多进程 + 多池子 + 显存）是确定的，收益是没量到的。

## 据实定队列并发度（T5 之后：解码那一路有数字了）

三个数**都不足以**定一个数字出来，理由如下：

| 想要的 | 缺什么 |
|---|---|
| 出片任务能并发几个 | 并发测量跑在 320x180 上，**真实尺寸下的数字没有** |
| 单机出片吞吐（帧/秒） | P6 已补上（14.56 / 22.50 ms 每帧）—— 但那是**单路**出片，不是并发；且与第七项那把尺子对不上账（见 7.4） |
| 能撑多少编辑用户 | loopback 上限有，**真实网络没有** |

**所以这里仍然不给一个"能同时跑几个出片任务"的数字。** 给了就是拿带边界的数当结论用 ——
而那正是这份文件开头说的、比没有数字更危险的事。

**但"解码那一路的并发数"现在有数字了**（第七项）：它是 **1**（一次一个源在读，
`pipeline.rs:649` 是阻塞读），代价与理由写在 7.4。这条不是"没量"，是"量到就是 1"——

方向性判断（标明它是方向性的）：

> 出片侧的并发**必须由队列限流**（GPU 只有一个 device，并发只会互相拖慢）；
> 编辑侧（素材取用）在服务端**不是瓶颈**，瓶颈在真实网络。
