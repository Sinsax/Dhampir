# 报告：与 V-Trim 的差异 · 性能 · 基座性质

> 这一份是**下阶段计划的前置展开**：先把事实量清楚，再谈要做什么。
> 所有数字都是这一轮实测的，出处写在每一项后面。

## 0. 先纠正一个词

「gasp」= **GSAP**。V-Trim 的精修引擎就是它（`vtrim-polish/src/lib.rs:1`：
「GSAP 精修引擎」），从 CDN 加载、跑在 headless Chrome 里。
它的 `polish --help` 也写着「GSAP 特效 + 字幕 + 弹幕 + 封面」。

我按**「性能还没赶上 V-Trim」**理解并做了实测。**结论与直觉相反**（见 §1）。

## 1. 性能：实测数字

### 1.1 头对头

| | V-Trim 0.2.1 | 本仓 |
|---|---|---|
| 墙钟 | **70.2 s** | **134.6 s** |
| 输出帧率 | **30 fps** | **60 fps** |
| 帧数 | **2907** | **5812** |
| **每帧** | 41.4 帧/秒 | **43.2 帧/秒** |
| 编码器 | `h264_nvenc`（硬编） | `libx264 -preset veryfast -crf 20`（软编） |
| 分块 | **4 块，各一个线程** | 1 条管道，串行 |
| 中间产物 | **每帧 JPEG q=0.6** | 无（直接 h264） |
| 时间基 | 源码 `timebase` | 同 |

出处：`vtrim.exe polish render --renderer chrome`（默认后端，跑在工程副本上）；
本仓 `dhampir render` 的 `elapsed_ms` + 墙钟。

### 1.2 结论

> **总耗时差 1.92×，几乎正好等于帧数差 2.00×。
> 每帧成本我其实略快（43.2 vs 41.4 帧/秒）。**

也就是说「性能没赶上」的主因**不是**架构劣于它，而是**输出帧率这个策略差异**：
V-Trim 把 60fps 的源**降到 30fps** 出片，我保留 60fps。

代价对比要说清楚：**V-Trim 的 1.92× 速度是用两项质量换来的** ——
① 一半的时间分辨率；② 每帧一道 JPEG q=0.6 的**代际损失**（这正是我一直在测的
「底噪约 6/255」的来源，它不是我测量的误差，**是它的真实管线**）。

### 1.3 我的 118.2 s 花在哪

| 段 | 实测 | 占比 |
|---|---|---|
| 编码 | `libx264 veryfast` 实测 **5.4 ms/帧** → 31 s | 26 % |
| 解码 + GPU 三趟 + 读回 + 文字 | 其余 **87 s**（15.0 ms/帧） | 74 % |

（`h264_nvenc` 实测 4.4 ms/帧 → 26 s，**只快 18 %** —— 硬编不是这里的关键。）

### 1.4 架构上真正的差距：**只有一条**

`vtrim-polish/src/render/pipeline.rs:173`：把时间轴劈成 `parallelism`（这里 4）块，
**每块一个 `std::thread::spawn`**，各自渲染 + 编码，最后 concat。

本仓是**单线程**：`for frame in from..=to { …submit… readback… write stdin }`，
而且每帧 `queue.submit` 之后**同步 `pollster::block_on` 读回**，
再**同步写进 ffmpeg 的 stdin** —— GPU、编码器、CPU 三者完全不重叠。

### 1.5 所以「性能」这一项的待办（按性价比）

1. **输出帧率进契约**（`render_hints.fps`，默认跟源或 30）—— 直接决定 2× 还是 1×
2. **分块并行**（N 个 worker 各渲一段再 concat）—— 唯一真正的架构差距
3. **硬编可选**（NVENC 探测 + 软编兜底）—— 白捡的 18 %
4. **不要为了速度引入 JPEG 中间产物** —— 那是拿质量换的，本仓不该跟

## 2. **最重要的发现：整条 Warp 特效管线是死的**

### 2.1 证据链

1. 转译出来的工程里有 3 条 `shake` 特效（`main-0` 两条、`main-2` 一条）
2. 把 20s 那一帧的 `shake` **整条删掉** → 逐像素差 **20.79 → 20.79**（一点没变）
3. 把 `amount` 从 0.02 改成 **0.2**（= 216 px，肉眼必然可见）→ **0.00**
4. 用一个**最小变体**（只剩一层、一条 `shake`、`window` 缺省 = `Always`）→ **0.00**
5. `shake` / `zoom_bounce` / `pulse` 三条**全部** 0.00

> **整个 `EffectPipeline::Warp` 级在本仓的 CLI 出片路径上没有任何效果。**

### 2.2 根因

`dhampir-core/src/render/timeline.rs:1341`：

```rust
for (index, layer) in layers.iter().enumerate() {
    ...
    if layer.is_adjustment {                     // ← 只有"调整图层"才会进调整级
        steps.push(Step::Adjust { layer: index, effects: layer.effects.clone(), … });
    }
}
```

**调整级（`PerPixel` / `Warp` / `Neighborhood`）的特效只在 `is_adjustment: true`
的图层上执行。** 而转译器把 `shake` 放进了 `main-0`（一条**普通视频图层**）的
`effects` 里 —— 于是它**通过校验、出现在 JSON 里、被求值层算出来，
然后被渲染器整条丢掉**。

### 2.3 这是「写好了没接上」的**第 5 次**，也是最大的一次

| # | 字段/特性 | 表现 | 谁抓到 |
|---|---|---|---|
| 1 | `Effect.window` / `Effect::strength` | 瞬时效果变成整段生效 | 早前 |
| 2 | `TRANSFORM_TARGETS` | 关键帧 target 拼错静默失效 | 早前 |
| 3 | `AudioPlan.overlaps` | 削顶看得见、叠加看不见 | 早前 |
| 4 | `CueStyle.color` | 逐条颜色永远不生效 | 上一轮 |
| 5 | **整条 Warp 级** | **shake / zoom_bounce / pulse 全死** | **本轮** |

前四次是"一个字段"，这一次是**一整条流水线级**（3 个特效类型）。

### 2.4 修法（不是补一行，是补一层语义）

调整级特效的语义是「**作用于它下面的一切**」——所以它天然属于**独立图层**。
转译器应该：

- 为一个时间窗特效**单独发一条调整图层**（`is_adjustment: true`），
  把 `in_frame` / `out_frame` 设成事件窗口，
- 于是**窗口基准问题一并消失** —— `Effect::strength(local, …)` 的 `local`
  是图层局部帧，图层一独立，"事件起点"自然就是 `local == 0`，
  不再需要 `transient` 窗口去模拟绝对时间。

顺带：本轮为了这个问题查出来的 `shake` 幅度口径 **也是错的**，
但**现在无所谓**（它根本不跑）：V-Trim 的 `intensity` 是**像素**
（`templates/index.html:983,2596` 的 `off` 直接进 `tl.to({x:off,y:-off})`），
本仓 `amount` 是**归一化位移比例** —— 我按 `intensity * 0.05` 写，
在 1080p 下是 **21.6 px，比 V-Trim 的 0.4 px 大 54 倍**。
修 Warp 那一层的时候要一起改成 `intensity / target_h`。

## 3. 效果：还差什么（全部量化）

| 项 | 现状 | 证据 |
|---|---|---|
| 平均逐像素差（13 个时刻） | **8.29** | 最差 20.79 |
| **`shake` 完全没做** | 见 §2 | —— |
| 运镜过渡中的缩放 | **差 1.5%** | 20s 那一帧把图放大 1.015 差就 **20.79 → 13.51** |
| 文字栅格化器 | 不可消除 | 字幕带是**连续**高差区（位置对、字形不同）；Chrome/Skia vs ffmpeg/FreeType |
| 贴纸 GIF 逐帧延时 | 只能表达均匀间隔 | V-Trim 用 `sticker_frames.json` 的 `delays` 数组 |
| 高亮词 | 未实现 | `filter.highlight` + `.cap .hl` |
| 封面 | 未实现 | V-Trim 有 `polish cover`（另一条产物通道） |
| 输出帧率 | 60 vs 30 | 见 §1 |

**20s 那一帧的 1.5% 缩放**是最值得修的一处：它把最差时刻从 20.79 拉到可能的 13.5。
疑似过渡的**起算/缓动**与 V-Trim 差 ~2 帧（`td = min(duration*0.5, 0.6)`，
`pow2_out(0.167) = 0.306` → `zoom = 1.3 + 0.2*0.306 = 1.361`）。

## 4. 基座性质：三个结构性问题

这一轮的四个错（弹幕窗口、逐条颜色、字号、Warp 级）**全部是同一类**，
而它们暴露的是**基座本身的机制问题**，不是零散 bug。

### 4.1 「两端可比」这个核心命题，缺一道守卫

基座的存在理由是「同一份工程 → 预览与成片可比的画面」。
但保持两端一致的机制目前是：**人工纪律 + 几条点状守卫**。

**实测反例（本轮新发现）**：

```js
// web/engine.js:31,66
const TEXT_FONT = "sans-serif";
ctx.font = line.font_px + "px " + TEXT_FONT;
```

浏览器预览 **不读 `font_weight`、也不读 `font_family`** ——
而 CLI 侧已经通过 `--font-bold-file` / `--font-dir` 两样都实现了。
于是同一份工程，**预览是常规 sans-serif、成片是雅黑粗体**。

这正好是基座最不该有的那类错，**而现有守卫抓不到它**：
`check-overlay-plumbing.mjs` 判的是「调用形不形在」，不是「字段覆没覆盖到两端」。

### 4.2 「有读数」掩盖了「没看图」

这一轮的四个错，在 13 个时刻的平均值上分别是
**−0.08 / −0.02 / −0.82 / 0.00** —— 平均值对它们几乎无感。
四个**全都是把出片和参照并排看**才发现的。

这说明当前验收口径（SSIM、平均逐像素差）**必要但不充分**。
缺的是**结构化的对照看图**：固定若干"一定会露馅"的帧
（瞬时特效中点、过渡中点、贴纸出场/退场、多行字幕），逐张比对。

### 4.3 契约能表达，不等于能被求值

`Effect::strength(local, duration, …)` 的 `local` 是**图层局部帧**，
而转译器想表达的是**事件绝对时间** —— 于是它用 `transient` 窗口去模拟，
而模拟出来的东西挂在错误的图层上、又被整条丢掉。
**契约没有错，是"用契约表达某件事"这条路上没有任何检查。**

## 5. 下阶段计划（建议，按依赖排序）

### 阶段 A — 把「静默失效」这一类根治（最高优先）

1. **修 Warp 级**：转译器为时间窗特效发独立调整图层（连带修 `shake` 幅度口径
   为 `intensity / target_h`）
2. **新守卫 `check-wired-fields.mjs`**：扫契约的 `pub` 字段，
   "除定义文件外全仓零引用" = 红灯（这能抓 §2.3 的表里 5 条中的 4 条）
3. **新守卫 `check-dual-end-coverage.mjs`**：对每个"影响画面"的契约字段，
   检查 **CLI 与预览两侧都引用**了它（这能抓 §4.1）
4. **修 `engine.js`**：把 `font_weight` / `font_family` 接进 `ctx.font`

### 阶段 B — 性能

5. **输出帧率进契约**（`render_hints.fps`）+ 默认策略
6. **分块并行渲染**（N worker + concat）
7. **硬编探测**（NVENC → 软编兜底）

### 阶段 C — 效果

8. **运镜过渡的起算/缓动对齐**（20s 的 1.5%，最差帧 −7）
9. **贴纸逐帧延时**（`AssetKind::ImageSequence` 加延时数组）
10. 高亮词（`filter.highlight`）

### 阶段 D — 验收口径

11. **结构化的对照看图**：固定帧清单 + 并排图 + 人眼过一遍
12. 封面（另一条产物通道，可独立排期）

## 6. 这一轮不动的东西（先说清楚）

- **不引入 JPEG 中间产物**换速度 —— 那是拿质量换的
- **不为了对齐 30fps 而丢掉 60fps 能力** —— 帧率是**配置**，不是写死的策略
- **文字栅格化器的差（Chrome/Skia vs ffmpeg/FreeType）不动** ——
  要抹掉它得把出片那一路也换成 canvas，那是另一个项目
