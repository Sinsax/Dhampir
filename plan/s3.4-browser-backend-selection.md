# S3.4 浏览器后端选择与视频源上屏 —— 探索记录（**未决**）

> 起因：浏览器预览在 Firefox 上**只能每帧 `createImageBitmap(video)`**，`?src=video` 直传会 panic。
> 需要判断「把 wgpu 的后端从 WebGPU 换成 GL/WebGL2」能不能换来性能。
>
> ⚠️ **本文不是决策。** S3.1 那种「实测数字 + 结论」的形状这里还不成立——**一个数都还没有**。
> 本文的产出只是把**已核实的事实**与**待决的两个数**钉下来：免得后人把同样这几个源
> 再查一遍，也免得把「上游已合并」误读成「现在就能用」。
>
> 写于 2026-09-30。**本次探索没有改动任何代码**，本文是唯一新增文件。

## 0. 一句话

Firefox 上「`<video>` 进不了 GPU」的根因**不在 wgpu**，在 **Gecko 的 WebGPU IDL 联合类型**——
wgpu 对 `<video>` 的支持一直都在（F7）。零拷贝那条路此刻卡在两处：
**wgpu 的 Web 后端还是 `unimplemented!`（上游修复已合并、尚未发布，F8/F12/F13）**，
以及**《WGSL 可移植性子集》禁隐式 LOD 采样**（[s3.1](./s3.1-source-frame-sampling.md) §2.2）。
换 GL 后端能绕开第一处，代价是一次**已记录架构决策的反转**（§4）。

## 2. 三句最容易被说错的话

这一节的用处是省掉下一轮的返工：下面三句都有人（包括我）说过，且都是错的。

| 说法 | 实际 |
|---|---|
| 「Firefox 的 `importExternalTexture` 会**回退**成 CPU 拷贝」 | **假。** 141–143 里这个方法**根本不存在**；不存在「回退」这种机制，它是 `undefined`。144 起才有（F2） |
| 「Firefox 的 wgpu **传不了** `<video>`，只能 bitmap」 | **半假。** wgpu 侧一直支持（F7）；挡住的是**浏览器的联合类型**（F3/F4）。这个区别决定了「换后端」是不是解法 |
| 「加个 fallback 退到 GL 就行」 | **假。** 后端在 `Instance::new` 就定死、换不了（§3）；而且它反转一条**已记录的决策**（§4） |

## 3. 机制：为什么这不是一个 fallback

1. **后端在建 `Instance` 那一刻定死。** 浏览器侧唯一的创建点是
   [`web.rs:110-115`](../crates/dhampir-wasm/src/web.rs)（注释自称"本 crate 里唯一与 native 不同的代码行"）。
   `Device` 建起来之后**不可能再换**——所以这不是"拷 video 失败就换条路"的 try/catch，
   而是**开跑前二选一，然后一次性建整套上下文**（Instance / Adapter / Device / surface / pipelines / 纹理）。
2. **触发条件必须在 JS 侧判。** 从 Rust 侧试 `copyExternalImageToTexture` 会撞上
   [engine.js:445-464](../web/engine.js) 记的那个 panic：wgpu 把 TypeError unwrap 成 panic，
   而一次 panic 会把 wasm 侧的 `ProjectHost` **永久借住**，之后任何调用都 `RefCell already borrowed`
   ——连"失败后退回 bitmap"都救不回来。现有探针（[engine.js:791-809](../web/engine.js)）正是为此写成纯 JS。
3. **它切换的是整个渲染栈**，不只是视频那一条路：compose / blur / color_adjust / warp / scene
   全都跑在被选中的那个设备上。
4. **"请求的后端"≠"实际跑的后端"。** 若把 `BROWSER_BACKENDS` 改成 union，
   [`backend_label()`](../crates/dhampir-core/src/gpu.rs) 会输出 `BROWSER_WEBGPU | GL` 这种形状，
   而它**说不出这一轮真正跑的是哪一个**——真正的答案在 `adapter.get_info().backend`。
   证据链（`corpus.rs:312` / `:527` / `:679` 写的 `requested_backends`）里这个键的含义要跟着重新定义。

## 4. 与已记录决策的冲突：代价比注释里写的小，但没有消失

[`gpu.rs:127-132`](../crates/dhampir-core/src/gpu.rs) 是一条**已记录的架构决策**：

> `BROWSER_WEBGPU` 对应页面里的 `navigator.gpu`。**不写 `WEBGL`**：
> WebGL2 的能力下限（没有 compute、没有 storage texture、没有 `texture_external`）
> 会让同一份 WGSL 在两个宿主上真的变成两份代码，那正是本架构要避免的事。

**核查这条理由在「今天」是否成立**——清点 `dhampir-core` 里所有 `BufferUsages` 构造点：

| 位置 | 用途 |
|---|---|
| `render/color_adjust.rs:140`、`render/blur.rs:151`、`render/color_mask.rs:206`、`render/compose.rs:374`、`render/scene.rs:895`、`render/warp.rs:167` | `UNIFORM \| COPY_DST` |
| `render/scene.rs:1010`、`render/probe.rs:325` | `VERTEX` |
| `readback.rs:287` | `COPY_DST \| MAP_READ` |

**没有 `STORAGE`、没有 compute pipeline。** 所以那条注释里的代价**被推迟到了未来**：
GL 后端今天能原样承载这份渲染图。三点补充：

1. **代价没有消失。** 一旦 GL 成为一条被支持的路径，"将来要用 compute"就变成枷锁——
   这正是那条决策当初要防的事，只是它防的是**未来**，不是现在。
2. 注释里提到的 `texture_external` 在 GL 上确实没有，**但这不是新增损失**：
   那条路已被 [s3.1](./s3.1-source-frame-sampling.md) §2.2 否掉（子集禁隐式 LOD 采样）。
3. **反转一条已记录的决策要按 s3.1 的规格落文件**（实测数字 + 结论 + 边界），
   不能靠改一行常量悄悄完成。

## 5. 要变成决策，缺哪两个数

| 数 | 怎么取 | 取值决定什么 |
|---|---|---|
| **A：Firefox 157 的适配器是真 GPU 还是软件回退** | 页面里读 `(await navigator.gpu.requestAdapter()).info` 的 `deviceType` / `architecture` / `isFallbackAdapter` | 决定「有没有必要动」——若 `deviceType` 是 `Other`/CPU，那才是"性能断崖"的来源 |
| **B：Firefox 上零拷贝 vs 现行 bitmap 的真实每帧成本** | 把 [s3-sampling-spike/index.html](../scripts/s3-sampling-spike/index.html) 的**路径 A**（纯 JS `importExternalTexture`）在 Firefox 上跑一遍 | 决定「零拷贝值不值得为它反转决策 + 给子集开例外 + 防 panic」 |

**判定表**（两个数出来之后照这张表走，不要凭感觉）：

| A | B | 动作 |
|---|---|---|
| 真 GPU | 零拷贝不明显更快 | **什么都不做。** 你们自己的数据显示 bitmap 那段是 0.00ms（[usage.md 6.5](../docs/usage.md)），改了只换来"未来不能用 compute" |
| 真 GPU | 零拷贝明显更快 | 值得走零拷贝，但先算 §6 的账（反转决策 + 子集例外 + 防 panic + `FrameSource` 加分支） |
| 软件回退 | 不要紧 | **走 GL 后端。** 它同时解决"适配器是软件实现"和"union 不收 `<video>`"，且**今天就能做**（F9，不需要升 wgpu） |
| 拿不到数 | — | **不改。** 没有数就不动已记录的决策 |

> 一个必须记住的前提：**「bitmap 慢」只在软件适配器上成立。**
> 真适配器上 4~6ms/帧、软件适配器上十几 ms/帧与整体 ~190ms/帧的对照在
> [engine.js:387-389](../web/engine.js)；而 6.5 节的 `--verdict playthrough` 拆解里
> `createImageBitmap` 与 `setBitmap` 都是 **0.00ms**，99% 的时间在 `seek`。
> 两处不矛盾：**它们说的是两种适配器**。所以数 A 不是可选项。

## 7. 边界（本次**没有**做的事）

- **没有在 Firefox 上跑过任何测量。** 本文一个性能数字都没有；F9 只证明"代码路径存在且可用"，
  **不证明** Firefox 的 `texSubImage2D(video)` 是 GPU 拷贝还是 CPU 回读。
- **没有定位到 Gecko 的 IDL。** `dom/webgpu/` 下没有 `.webidl`，`dom/webidl/GPUQueue.webidl` 也 404。
  所以「Firefox 157 的联合类型仍不含 `<video>`」**以本仓探针的输出为准**，不是本文的结论——
  探针会把浏览器的原话打出来（`engine.js:806-808`）。
- **没有验证上游修复能否在本仓工具链下编过**（rust-toolchain 1.97.0 / MSRV 1.87）。
- **没有跑全仓 18 个守卫。** 只单独验了本文：`inspectBytes` 给 `problems=[]`（0 个 CR、无 BOM、合法 UTF-8）。
  另外记一笔环境状态：`node scripts/check-text-hygiene.mjs` 在**全仓范围本来就是红的**——
  15 个 `out/*.txt`（未跟踪的本地日志，PowerShell 写的 BOM + CRLF）不在守卫的 `SKIP_DIRS` 里，
  而 `out/` 一个被跟踪文件都没有（`git ls-files out` 为空）。**那是本次之前就有的，与本文无关**；
  要让它全绿，得单独决定 `out/` 是清掉还是加进 `SKIP_DIRS`。
- **本文目前是孤儿文档**：没有从 `next-steps.md` / `video-editor-plan.md` 挂链接——
