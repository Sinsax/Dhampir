> **产出**：M2 / T2.5。**上游**：指导文档 §4.3①（"始终按 WebGPU 的能力下限写"）、§4.3②（双编译器）、§4.3③（浮点确定性）。

## 1. 口径（先读这段，再看表）

- **计数一律在剥掉注释后的代码上做。** 两份着色器的文件头都写着"不用导数"；不剥注释的话，这道闸会去举报它自己的文档，而下一个人的修法通常是**把闸删掉**——那比误报更糟。
- **允许表是"穷尽"的，禁止表不是。** 允许表列的是**当前两份着色器用到的全部构造**：用了却没在表里的，普查直接红。禁止表只有 6 条，是"**下一份**着色器也不许用"的那几条。
- **不同条目的计数会重叠，不能相加。** `f32` 也会数到 `vec2<f32>` 里那个 `f32`。这张表是"逐条构造各出现多少次"，不是互斥分类——加起来的数没有含义。
- **词首匹配是故意保守的。** `fwidth` 也会命中 `fwidthCoarse`，`loop` 也会命中 `loopback`（这一个确实是误报）。方向必须这样定：守卫用的是 `contains()`，普查要是比守卫**钝**，就会出现"普查说 0 次、`cargo test` 却红了"的死角。
- **允许表里"是哪一对宿主"不重要。** 允许表只说"这份文本用了什么构造"，与它跑在浏览器还是 native 无关——两份 `.wgsl` 是**同一份文本**供两个编译器读（`dhampir-core` 里 `include_str!` 进去，wasm 侧把原文交给 Tint）。

### 容易被问到的三个"为什么不在表里"

- **`textureSampleLevel(`（允许，但当前没用到）**：它显式给出 LOD，不需要导数，属于子集；只是本仓现在一律 `textureLoad`。禁词表里写的是带左括号的 `textureSample(`，就是为了不把它一起吃掉（`wgsl_subset.rs` 里有一条用例钉着"别改回去"）。
- **`if (` / `for (` / `while (`**：不在允许表里。现在两份着色器一个分支都没有——**不是**因为分支本身可怕，而是因为分支一旦带副作用（写入、提前返回），差异就会变成"哪条路走了"的问题。要加分支时：先加进本表，并想清楚它在两个编译器下是否同一条路。
- **`sampler`**：不在允许表里。用法式滤波的采样器把 LOD 选择和滤波精度交给实现，而"累加顺序"这条线索会被滤波噪声盖住（blur 场景的注释里写了这件事）。

## 3. 禁止的构造（6 条，机器判）

这份表是从 `crates/dhampir-core/src/render/wgsl_subset.rs` 的 `FORBIDDEN` **读出来**的——**唯一一份来源**在那里，
普查工具也是从同一个常量解析的（两边手抄一份，迟早会漂移成"一边改了、另一边还是过得去"）。

| 禁词 | 理由（守卫里的原文） | 为什么它会进禁词表 |
|---|---|---|
| `fwidth` | 导数：结果允许因实现而异，基准用例里不能出现 | 两个编译器 + 两个驱动各自决定怎么算差分，结果**允许**不同 |
| `dpdx` | 导数：结果允许因实现而异 | 同上 |
| `dpdy` | 导数：结果允许因实现而异 | 同上 |
| `textureSample(` | 隐式 LOD 采样：它内部要导数；采样一律走 textureLoad | 它要算导数来选 mip 层，于是"差异来源"和导数叠在一起 |
| `loop` | 循环：累加顺序会交给编译器，而顺序必须由文本决定 | 展开顺序由编译器决定 = 同一份文本可以有不同累加顺序 |
| `atomic` | 原子：跨运行时的结果不可预期 | 顺序由调度决定，不由文本决定 |

**这 6 条是"下一步不写"的清单，不是"当前构建"的清单。** 它们红了就是红了，没有例外程序——理由都在表里，想让某一条通过，得先改 `wgsl_subset.rs` 里的理由，那是一次公开的决策改动，不是一次"顺手放宽"。

## 4. 替代写法（按"你本来想写什么"索引）

| 你本来想写 | 写成 | 为什么这样是可移植的 |
|---|---|---|
| `fwidth(...)` 做边缘 / 抗锯齿 | 边界由**整数**运算定（本仓做法：格子边长、条带边界都是精确的 1/8、1/4） | 边界不经过浮点判断，就不存在"模糊区域" |
| 隐式 LOD 采样 `textureSample(t, s, uv)` | `textureLoad(t, vec2<i32>(x, y), 0)`（按整型坐标精确取）；需要 LOD 时 `textureSampleLevel(` 显式给层 | 取哪个纹素由文本里的整数决定，不由导数决定 |
| 采样器做的 clamp / 滤波 | 自己写 `clamp(...)` + 无滤波读取（`load_texel`） | 滤波精度是允许实现降精度的；自己写就没有那块自由度 |
| 循环累加（模糊抽头之类） | **展开写**（7 个抽头写 7 行） | 累加顺序由文本决定，不由编译器展开顺序决定 |
| 需要按条件的循环 | 定长展开 + `select(` 把不需要的项掩掉 | 两端都求值 = 没有"走了哪条路"的分叉 |
| 跨像素累加（直方图、降采样计数） | 多趟渲染（每趟一个 pass，读上一趟的纹理） | 顺序由 pass 顺序决定，不由线程调度决定；`atomic` 因此也不需要 |
| 精度不确定的浮点 | 显式 `f32` / `u32` / `i32` + 显式转换 | 不写 `mediump` / `f16` 这类精度限定，就不存在"实现自己挑精度"的空间 |

## 5. 五个高危区

这几处**不是禁词**（工具抓不到），是"写的时候必须停下来想一下"的地方。碰到它们时，改动要带上"两个宿主是否还一致"的证据。

1. **`fract` / `pow` 的极限行为。**
   `fract` 在接近 1 的输入上、`pow` 在超大 / 超小指数上，规范给的是"近似到什么程度"而不是逐位相等——`pow` 的余量比四则运算大。
   本仓现状：`fract` 只作用在"已经是 [0,1) 附近"的值上（uv + 整数平移量），`pow` 只用在 sRGB 解码段（底 ≥ 0.055、指数固定 2.4，落在良性区间）。
   **要碰的话**：先把极限输入列出来（0、极小数、极大数、正好在分段点上），并加一条断言把"分段边界两侧"钉住。
2. **导数依赖（`fwidth` / `dpdx` / `dpdy`）。** 这条已经是禁词，列在这里是因为**最容易被"顺手"加进来**——比如为了抗锯齿。
   要加必须先回答："它在 Tint 和 naga 下是否同一条表达式？"现在没有能力回答这个问题，所以不进子集。
3. **长链累加。** 加法不结合，重排就换结果。三个办法按优先级：**展开写**（本仓做法）→ 缩短链（分成两趟）→ 用二进制可精确表示的数（**反例**：不能靠"权重取 1/16 就精确了"来救顺序问题——那会让"顺序由文本决定"这条守卫变成空话，blur 场景的注释里写了这件事）。
4. **非规格化数与精度限定。** 极小值附近的实现自由度最大；本仓的**规矩是"不依赖"**：不写精度限定（`mediump` / `f16`），所有浮点显式 `f32`，且不让极小值参与判定。
   诚实的边界：这份子集**不声称**"f32 逐位可移植"——跨厂商实测里 `alpha_stack` 全图 1 LSB 就是这么来的（见 §6）。子集能做的是把差异**压到可归因**。
5. **纹理采样的 LOD 语义。** `textureLoad` 的 mip 层是显式参数（本仓恒 0），`textureSampleLevel` 也是显式的；隐式的那个（`textureSample`）要导数，所以禁。
   还要记一笔：**滤波精度允许实现降精度**——这就是"不用采样器滤波、自己 `clamp` + 整数取样"的理由。

## 6. 差异归因清单（T2.5 的产出）

**判据来源**：`records/m2/framediff-crossvendor/`——`shape.json`（`--shape` 落的形状证据）、`verdict.json`（判定）、`report.txt`（人读的一页）。
这一对运行时：**甲 = 浏览器 WebGPU / AMD Radeon(TM) Graphics（驱动 32.0.21030.2001，Chrome 153 无头）**，帧集摘要 `bc09803eb44beac8`；
**乙 = native DX12 / NVIDIA GeForce RTX 4070（驱动 32.0.16.1074）**，帧集摘要 `4bc004b502a1301a`。各 80 帧。
档位：`scripts/framediff-thresholds.toml`（摘要 `3f9560d1e3d4fb3f`）。
形状口径：**有符号差写作「甲 − 乙」**（`shape.json` 的 `signed_delta_definition`），`plus` = 甲比乙亮；
`per_channel` / `sign_quadrant` 数的是**通道实例**（像素 × 通道），`diff_pixels` / bbox 数的是**像素**，**两套不能相加**；并集与逐帧分开记。

**bad case 库现状：空。** 上表 6 条没有一条判为"必须修"。这是本里程碑的结论，也是它的边界——
**它只对"这两个厂商 + 这五个场景"成立**。下一块卡（Intel Arc、Apple M 系）进记录时，这张表要么被验证、要么被改写。

**这条清单与"哪些差异进 bad case"的关系**：这里的判定是**"是否可接受"**，不是"是否解释清"。`shape.json` 能证明的是**差异长在哪、多大**（事实），
"它是量化边界舍入"是**与形状一致的推断**（推断）。要让推断升级成事实，得构造"只改一处变量"的实验（一次只改一个变量——这条纪律在 T2.4 也用过）。

## 7. 这道闸的边界（明确不做）

- **不引 WGSL 解析器做语法级验证。** 普查是按 token 数的，不建语法树——它抓得住"冒出一个没申报的构造"，抓不住"用对了构造但写错了逻辑"。后者靠 corpus 比对（`records/m2/framediff*/`）。
- **不追求"允许表 = WGSL 全集"。** 表里只有**在用**的构造。写法上更希望它**短**：每加一行都是一次决策。
- **不做跨编译器差异的自动归因。** 那是 §6 那张清单的活，人读形状、下结论。
- **不含 `dhampir-worker` / 宿主代码的 WGSL 规矩**（M2 时它们还没有着色器）；同理也不含 M4 之后的特效着色器——到那时按同一套判定重跑，表会变长，这是预期的。
