# S3.2 proxy 生成规格 —— 决策

> M3 前置 spike 之二（plan §6）。也是指导文档 §11.3 要求的「proxy 生成规格 + 命令」那一份。
> 数字来自实机实测，复现方式见文末。测于 2026-09-22。

---

## 1. 为什么要有这份规格

素材管线的一致性来源：浏览器侧**只解 H.264**、只解 proxy（M3 T3.2 的有意取舍——不引 FFmpeg WASM）。
于是"素材长什么样"这件事必须在服务端一次定死，浏览器只负责解。规格里**每一个 flag 都影响预览体验**，
不是随手抄来的参数。

---

## 2. 规格（命令）

### 2.1 视频代理

```bash
ffmpeg -i src.mp4 -vf scale=-2:720 \
       -c:v libx264 -preset veryfast -g 60 -keyint_min 60 -sc_threshold 0 -crf 23 \
       -c:a aac -b:a 128k proxy.mp4
```

| flag | 取值 | 为什么 |
|---|---|---|
| `scale=-2:720` | 高度 720、宽度按比例取**偶数** | 宽度必须是偶数（H.264 的 4:2:0 色度取样要求），`-2` 而不是 `-1` 就是为了这个 |
| `-g 60` / `-keyint_min 60` | 每 60 帧一个 I 帧 | 60fps 素材下 = **1 秒 1 个关键帧**。**关键帧密度直接决定 seek 手感，比分辨率重要得多** |
| `-sc_threshold 0` | 关掉场景切换插入关键帧 | 否则画面一变就多插一个 I 帧，**间隔不再均匀**，seek 延迟变成"看内容" |
| `-crf 23` | 质量档 | proxy 是给预览看的，不是交付件；23 是 x264 的常用默认档 |
| `-preset veryfast` | 编码速度 | 素材导入时的等待时间 |
| `-c:a aac -b:a 128k` | 音轨 | 源**无音轨时 ffmpeg 自动跳过**，不需要额外分支（实测 EXIT=0） |

### 2.2 封面图（时间线缩略图的单张）

```bash
ffmpeg -i proxy.mp4 -vf "select=eq(n\,0)" -frames:v 1 -q:v 3 cover.jpg
```

### 2.3 雪碧图（时间线缩略图带）

```bash
ffmpeg -i proxy.mp4 -vf "fps=1/5,scale=160:-1,tile=10x10" -frames:v 1 -q:v 3 sprite.jpg
```

`fps=1/5` = 每 5 秒取一帧；`tile=10x10` 一张图装 100 格 → **一张雪碧图覆盖约 500 秒素材**。
长素材超出部分按张切分（`-frames:v` 那一步的产物按序编号），前端按 `(t, x, y)` 取格。

| 产物 | 命令 | 体积 |
|---|---|---|
| 封面图 | §2.2 | 47,111 B（1280×720, q=3） |

### 3.1 关键帧归一化（这条是规格的核心价值）

**规格不是"复制源的关键帧布局"，而是"把它归一化"。** 拿一个关键帧稀疏的源验证：

| 文件 | 帧数 | 关键帧数 | 首个 | 间隔 | 最大间隔 |
|---|---|---|---|---|---|
| `sparse1080p.mp4`（`-g 250`） | 480 | **2**（第 0、250 帧） | 0 | 250 | **250 帧 ≈ 4.2 s** |
| `sparse-proxy720p.mp4`（按 §2.1） | 480 | **8** | 0 | **60** | **60 帧 = 1.0 s** |

稀疏源进、均匀代理出。**最长 seek 距离被压到 1 秒**——不随源的编码习惯漂移。

## 4. 怎么验一个代理合规

```bash
# 分辨率 / 编码 / 帧数
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,nb_frames -of json proxy.mp4

# 关键帧间隔（应为 {60}，且首个在 0）
ffprobe -v error -select_streams v:0 -show_entries frame=key_frame -of csv=p=0 proxy.mp4
```

⚠️ **踩过的坑**：`ffprobe` 的 `csv=p=0` 输出**带尾逗号**（实测首行是 `1,\r`）。
拿 `line === '1'` 去数关键帧会**静默少算**——本规格第一版就把它数成了"首个关键帧在第 60 帧"、
"只有 7 个"，而真相是"首个在第 0 帧、共 8 个"。请按 `/^1/` 之类的**前缀**判。

## 5. 边界（这次没测的）

- **只测了合成素材**（`testsrc2`）。真实素材的运动/噪点会推高码率，`-crf 23` 的实际体积要按真素材再标一次。
- **没测音轨**：源无音轨，音频那一段只验证了"不报错"，没验证 `aac/128k` 的实际表现与音画同步。
- **没测 4K/HEVC 源**；`scale=-2:720` 对超大源的缩放成本未量。
- **没测色彩/HDR**：HDR 源经本管线会被压成 SDR，这条没验，也不在 M3 范围。
- **没测雪碧图的格子索引约定**：`tile` 的填充顺序（左→右、上→下）是 ffmpeg 的实现约定，前端要按它取格，本轮没做端到端验证。

## 6. 复现

```bash
# 1080p 测试源
ffmpeg -y -f lavfi -i testsrc2=size=1920x1080:rate=60 -t 8 -c:v libx264 -preset veryfast \
  -g 60 -keyint_min 60 -sc_threshold 0 -crf 23 -pix_fmt yuv420p target/s3/source1080p.mp4

# 代理（§2.1）
ffmpeg -y -i target/s3/source1080p.mp4 -vf scale=-2:720 -c:v libx264 -preset veryfast \
  -g 60 -keyint_min 60 -sc_threshold 0 -crf 23 -an target/s3/proxy720p.mp4

# 关键帧归一化的对照（§3.1）
ffmpeg -y -f lavfi -i testsrc2=size=1920x1080:rate=60 -t 8 -c:v libx264 -preset veryfast \
  -g 250 -sc_threshold 40 -crf 23 -pix_fmt yuv420p target/s3/sparse1080p.mp4
ffmpeg -y -i target/s3/sparse1080p.mp4 -vf scale=-2:720 -c:v libx264 -preset veryfast \
  -g 60 -keyint_min 60 -sc_threshold 0 -crf 23 -an target/s3/sparse-proxy720p.mp4
```
