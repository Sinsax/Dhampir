## 一条要写下来的教训（这一阶段反复踩）

**验证要验「那段代码能不能跑」，不是「逻辑对不对」。**

这一阶段同类错误出现过多次，最典型的是第 35–36 轮：
我用 `node -e` 单独验了正则表达式，就写下「确认：阈值逻辑正确」——
而**文件里根本没有那个 `const` 声明**，脚本一跑到那里就 ReferenceError 崩掉。
「崩溃」在外面看起来与「没输出」一样，于是我又**猜**了一个原因（stderr 被吞），**也猜错了**。

由此固化下来的两条：

1. **声称什么，就单独去验什么。** 尤其是窗口总数 ÷ 净变化 ÷ 编译通过——这些都不等于「功能生效」。
2. **先建观测，再动代码。** 卡住比失败难查；「什么都没发生」是不可诊断的状态，先让它是可诊断的。

## 一个 bug 的完整归因过程（第 59→62 轮）

定义性用例第一次跑**失败**。我没有去改实现或改断言，而是：

1. **先归因**：让两边都走同一条路径 → **排除**「搬运引入差异」；
2. **再定位**：查源的 alpha → 一行定性；
3. **最后落地**：用 `edit` 而不是 `node -e`，一次成功。

**根因**：`synthetic_source_rgba8`（core 第 446 行）造的源**故意是半透明的**
（`alpha = if (x/16 + y/16) % 3 == 0 { 255 } else { 200 }`，core 里还有测试断言「不透明度应当有变化」）。
而**混合用的是源 alpha，不是图层 opacity** —— 所以「顶层 opacity=1.0 就能铺满」这个前提从来就不成立。
**是判据的前提问题，不是实现问题。**

修法：加 `make_opaque_source`（alpha 全设 255），测试改用它。

## 最有分量的一条证据

**后端管道吃样本工程，与浏览器那条路三者完全一致：**

    本管道：  30/1 fps,  3.000000 秒,  90 帧
    浏览器：  30/1 fps,  3.000000 秒,  90 帧

两条完全不同的渲染路径（浏览器 wasm + WebGPU / 后端 native + FFmpeg）对**同一份工程**
产出同一个成片形状 —— 因为它们走的是**同一份核心渲染代码**。

**边界（写明的）**：这比的是**成片形状**，不是逐像素。逐像素比要求两端吃同一份像素，
那要求 worker 接上解码器并接受外部喂帧 —— **当前架构下不可测**（见 consistency-criteria.md）。

## 四项测量

| 项 | 结果 | 限制 |
|---|---|---|
| 渲染吞吐 | 13.35 ms/帧 | 合成源，不含解码 |
| GPU 并发 | 2 个并发比值 1.15 | 320x180 太小，不能外推 |
| 素材 IO/延迟 | 385 MB/s；单分片 p50 2.1 ms | loopback 上限 |
| 解码 | 0.46 ms/帧（只解码）；**4.17 ms/帧（含搬像素+上传）** | 合成片，是下界 |

**「拿到一帧」的成本里解码只占 11%** —— 这条分解比任何单个数字都有用。
