# S3.1 源帧采样策略 —— 决策

> M3 的**第一个决策**（plan §6「前置 spike」说它"本里程碑最重要"，结论必须落文件）。
> 本文的数字全部来自实机实测，复现方式见文末。测于 2026-09-22。

---

## 1. 要定的是什么

预览侧（浏览器）的源帧怎么进 GPU。三条候选：

| 选项 | 做法 | 代价 |
|---|---|---|
| **(a) 零拷贝外部纹理** | `importExternalTexture` → WGSL 里 `texture_external` + `textureSampleBaseClampToEdge` | 采样自由度受限（无 mipmap、无 repeat）；**WGSL 文本必须与 native 分叉** |
| **(b) `copyExternalImageToTexture`** | 每帧一次真拷贝进普通 `texture_2d` | 放弃零拷贝；换来两侧 WGSL **完全同文**、采样语义完全自由 |
| **(c) 混合** | 默认 (a)，遇到要 mip/repeat 的特效切 (b) | 两套路径都要维护 |

**决策依据**（plan 原文）：1080p 下实测 (b) 的拷贝成本 vs (a) 的约束成本。

---

## 2. 实测

环境：Windows / Chrome（headless=new，`--headless=new`）/ NVIDIA **lovelace** 架构 / wgpu 30 栈。
素材：`target/s3/source1080p.mp4`（1920×1080、60fps、8s、每 60 帧一个关键帧，FFmpeg libx264 生成）。
方法：页面把视频**暂停**在同一帧上，量**稳态每帧成本**；每次迭代 `submit → await queue.onSubmittedWorkDone()`。
样本 200 次（另有 20 次预热）。**全程零 WebGPU 错误**（驱动会拒绝有错的结果）。

| 路径 | mean | median | p95 | min |
|---|---|---|---|---|
| **A** `importExternalTexture` + 渲染 | 3.234 ms | 3.1 | 4.1 | 0.4 |
| **B** 仅 `copyExternalImageToTexture` | 3.6735 ms | 3.7 | 5.0 | 2.8 |
| **B** 拷贝 + 渲染 | 3.2755 ms | 3.3 | 4.9 | 0.9 |

派生：`copy_render − import_render = +0.0415 ms`。

### 2.1 像素关系（这一条比成本更重要）

同一帧、两条路各渲一张 1920×1080 RGBA8，整幅逐字节比对：

| 比对 | 不同字节 | max\|Δ\| | 结论 |
|---|---|---|---|
| **A vs B** | **0** | **0** | **逐字节相同** |
| A vs B（V 翻转后） | 704566 | 255 | 翻转确实会变——说明图案不对称，上面的"相同"是真结论 |
| B vs B（V 翻转后） | 704566 | 255 | 同上 |

**两条路的输出逐字节相同**：浏览器对源帧做的 YUV→RGB 与色彩处理在两条路上是同一套。
也就是说 **(a) 与 (b) 在保真度上没有区别**，(a) 换来的不是画质而是"少一次拷贝"。

---

## 3. 归因：一次差点写错的结论（值得留档）

第一次跑出来的数字是 **copy 只要 0.121 ms**、且 **A vs B 差 75% 的字节、max|Δ|=255**。
如果直接采信，结论会变成"拷贝几乎免费，但两条路颜色差很多"——**两条都是假的**。

真相是**我自己的 bug**：Dawn 要求 `copyExternalImageToTexture` 的目标纹理**同时带
`RENDER_ATTACHMENT`**，我只给了 `COPY_DST | TEXTURE_BINDING`。于是每一次拷贝都被校验拒绝、
**静默失败**（错误只在 `onuncapturederror` 里），纹理保持未初始化：

- "拷贝只要 0.12 ms" = **失败调用**的耗时；
- "B 渲染出黑图" → A vs B 自然差得多；
- "翻 V 不变" = 黑图翻不翻都一样（这一条把疑点坐实了）。

修法：目标纹理补 `RENDER_ATTACHMENT`；并且**驱动层加了硬闸**——结果里带任何 WebGPU 错误就拒绝出结论。
**教训**：一个"便宜得反常"或"差得反常"的数，先归因再采信。

---

## 4. 结论

**选 (b)：`copyExternalImageToTexture`。**

理由按权重排：

1. **输出逐字节相同**（§2.1）→ (a) 不带来任何保真收益。
2. **成本差在噪声内**：`copy+render` 与 `import+render` 差 **+0.04 ms**，而单独拷贝 3.67 ms 与
   零拷贝路径的 3.23 ms 也在 ~0.4 ms 之内。1080p 下**两条路一样贵**。
3. **(a) 要付的约束成本是结构性的**：`texture_external` 只能配 `textureSampleBaseClampToEdge`，
   没有 mipmap、没有 repeat，而且**WGSL 文本必须与 native 分叉**——这与底座的立身之本
   （同一份 WGSL 服务两个宿主）直接冲突。(b) 让两侧保持**同文**，采样语义完全自由。
4. (c) 是 (a) 的复杂度加上 (b) 的实现，在 (a) 已经没有收益可用时只会更糟。

**对底座接口的直接影响**：`dhampir-core::io` 里那条"已知张力"（`frame_view` 返回
`wgpu::TextureView` 装不下外部纹理）**解除**——因为选 (b) 之后，预览侧交给渲染图的
就是一张普通 `texture_2d`，与 native 侧走同一个 trait、同一种绑定。
**不需要给 `FrameSource` 增加"外部纹理"分支。**

---

## 5. 边界（这次没测的，别当成测过了）

- **量的是同步每帧延迟**（每次 `submit → onSubmittedWorkDone`），不是流水线吞吐。
  真实预览里提交与渲染重叠，**边际成本会比这个数小**；但 A/B 是同一把尺子，比较仍成立。
- **只测 1080p、只测一块卡（NVIDIA lovelace）**。4K、核显、其他厂商未测。
- **素材是合成图案**（`testsrc2`），色彩复杂度低于真实素材；结论只覆盖"拷贝与采样"本身。
- **未测 `VideoFrame` 生命周期**（S3.3 的活）：`close()` 时机不对会耗尽显存，这条与采样策略正交。
- **未在真实播放中测**（本实验是暂停帧的稳态）；播放中每帧源都在变，是否引入额外同步开销未验。

## 6. 复现

```powershell
# 1. 造 1080p 素材（1080p、60fps、每 60 帧一个关键帧）
ffmpeg -y -f lavfi -i testsrc2=size=1920x1080:rate=60 -t 8 -c:v libx264 `
  -preset veryfast -g 60 -keyint_min 60 -sc_threshold 0 -crf 23 -pix_fmt yuv420p target/s3/source1080p.mp4

# 2. 跑实测（自动起服务、起无头 Chrome、页面自己量、驱动先验后信）
node scripts/s3-sampling-spike/run.mjs
node scripts/s3-sampling-spike/run.mjs --self-test   # 结果自洽性校验，8 条断言
```

页面：`scripts/s3-sampling-spike/index.html` ｜ 驱动：`scripts/s3-sampling-spike/run.mjs`
驱动会拒绝：分辨率不是 1920×1080、样本数不足、像素覆盖不完整、**任何 WebGPU 错误**。
