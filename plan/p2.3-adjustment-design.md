# P2.3-2 设计：调整图层的分段合成

> 这一步一直没做，理由一直是「它需要一次性完成」。**但那个理由和做法都没被写下来** ——
> 于是每轮都要重新想一遍。这份文件就是把它写下来，好让下一轮**直接实现**。

## 一、目标语义

调整图层影响「**在最终合成顺序里已经画上去的全部内容**」。
求值层已经把 tracks 拍平成一个列表，所以有精确落点：影响它**之前**的层，不影响之后的。

    原来： [层1][层2][调整A][层3]   -> 一次 pass 全叠完   ✗ 表达不了

    改成： Draw(0,1) -> Adjust(2) -> Draw(3)
           段1 合成到中间纹理 t1
           t1 过 A 的特效 -> t2
           t2 + 层3 -> 最终

`plan_steps` 已经能给出这个计划（P2.3 第一步，已测住）。

## 二、**先要解决的障碍**（不先解决就写不下去）

`Compositor::compose` 的 `load` **永远是 `LoadOp::Clear(clear)`**
（`render/compose.rs` 第 330 行）。

也就是说：**它每次调用都会把目标清空**。
而分段合成恰恰要求「把第 2 段合成到第 1 段已经画好的底上」——
直接套用现有 compose，第二段会把第一段擦掉。

所以第一步是把它的 `clear: wgpu::Color` 改成 `clear: Option<wgpu::Color>`：
`Some(color)` 保持现在的行为（Clear），`None` 变成 `LoadOp::Load`。
这个改动**不影响任何现有调用方** —— 它们传 `Some(...)` 即可，行为逐字节不变。

**这条是本设计里最容易被忽略的一处**：不知道它，写出来的分段合成会「看起来对、结果不对」，
而症状是「调整图层之前的内容不见了」—— 很容易被误判成纹理绑定错。

## 三、实现步骤

1. `Compositor::compose` 的 `clear` 参数改成 `Option<wgpu::Color>`；
   现有调用方传 `Some(...)`（行为不变，可逐字节验）。

2. `TimelineRenderer::render_frame` 里，当 `plan_steps` 含 `Adjust` 时走新分支：
   * 建两张 **ping-pong 中间纹理**（`RENDER_ATTACHMENT | TEXTURE_BINDING`，与 target 同格式同尺寸）；
   * `current` 指向第一张；
   * 按 plan 走：
     - `Draw(indices)`：把这几层合成到 `current` —— **第一段用 `Some(clear)`，后续用 `None`**（关键）；
     - `Adjust { effects }`：用现成的 `BlurRenderer::blur_separable` 从 `current` 画到另一张，交换 `current`；
   * 结束时若结果不在 target，用现成的 `BlitRenderer` 拷到 target。

3. 退化情形要显式处理：
   * **调整图层在最前**：它下面什么都没有 —— 对**空底**跑特效，不崩、也不该凭空产生内容；
   * **只有一个调整图层**：计划里没有 `Draw` 步，`current` 从未被画过 —— 拷到 target 时应当是空的；
   * **没有调整图层**：走原来的单 pass 路径（`plan` 只有一个 `Draw`），**行为逐字节不变**。

## 三·补：**第 2 步拆不开**（试过了，记下来免得再试）

第 1 步能拆出来单独做（清掉 compose 的清屏障碍），但**第 2 步不能**。

试过三个拆法，都会触发「never used」警告 —— 而本项目把警告当回归：

| 想先做的 | 为什么不行 |
|---|---|
| 先加建 ping-pong 纹理的辅助函数 | 没有调用方 → 「never used」警告 |
| 先加「对某个纹理跑调整特效」的辅助函数 | 同上 |
| 让现有单 pass 路径也走「先画进纹理再 blit 到 target」 | 能用上辅助函数，但**给热路径白加一次 blit**，是性能回归 |

所以**第 2 步必须一次写完**：ping-pong 纹理 + 按 plan_steps 循环 + 终点落回 target。

这与第 1 步的差别在于：第 1 步改的是一个**已有调用方**的函数签名，
它天然有使用点；第 2 步是**新增一条分支**，而分支里用到的每样东西
在分支写完整之前都没有调用方。

**可执行的建议**：写第 2 步时，把 render_frame 现有那段
（备纹理 → 建 LayerDraw → compose）先抽成一个**带目标参数的**私有函数，
然后**在同一次改动里**既让原路径调用它（传 target），
又让分段路径调用它（传中间纹理）。
这样抽出来的函数**一出生就有两个调用方**，不会有警告。

## 三·再补：**我第 48 轮的「拆不开」结论是错的**，以及真正的障碍

### 更正

我当时写：「第 2 步拆不开 —— 提前提取的辅助函数没有调用方，会触发 never used」。

**那不对。** 提取出来的辅助函数**由现有的单 pass 路径调用**，它立刻就有调用方；
第二个调用方（分段路径）下一轮再加就是了。**不需要一次写完。**

所以第 2 步的正确拆法是：

1. **本轮**：把「备纹理 → 建 LayerDraw → compose」抽成 `compose_layers(dest, clear, ...)`，
   由现有单 pass 路径调用它（传 `dest = target`、`clear = Some(clear)`）。
   纯重构，**行为逐字节不变**，真机 GPU 可验。
2. **下一轮**：加第二个调用方 —— 分段路径传中间纹理与 `None`。

我当时把「这个函数在**最终形态**下要有两个调用方」错听成了「现在就必须有两个」。
**这是把"终局"当成了"此刻的前提"。**

### 真正的障碍（写下来免得踩）

抽出来的辅助函数会遇到一个**资源生命周期**问题：

模糊用的那两张临时纹理（`blurred` / `intermediate`）在函数内创建，
而它们必须**活到 pass 被提交之后**。`render_frame` 现在靠函数末尾的 `drop(keep_alive)` 表达这件事
（注释里写着「让编译器和读者都看得见这些纹理活到了这里」）。

**一旦把这段挪进辅助函数，纹理会在函数返回时就析构** —— 而命令缓冲仍引用它们。
症状不是编译错误，而是**随机的画面错乱或 GPU 校验错误**，极难归因。

**所以辅助函数必须把那些纹理交还出来**：

    fn compose_layers(...) -> (usize, Vec<wgpu::Texture>)

调用方持有返回的 Vec 直到提交，再 drop。**这是签名的一部分，不是实现细节。**

## 三·三补：**上一节那条「必须交还纹理」被我说重了**（更正）

上一节我写：「辅助函数必须把临时纹理交还出来，`fn compose_layers(...) -> (usize, Vec<wgpu::Texture>)`，
否则纹理会在函数返回时析构，而命令缓冲仍引用它们。」

**后半句不成立。** 提取之前 `render_frame` 的写法就是：

    // 让编译器和读者都看得见这些纹理活到了这里。
    drop(keep_alive);
    draws.len()

**它主动在函数末尾 drop 掉了那些纹理** —— 而调用方是在这之后才 `queue.submit(...)` 的。
也就是说：**如果"drop 就等于资源立刻消失"，现有代码本来就是错的。**

它没错，因为 **wgpu 会把在飞命令缓冲引用的资源保活**：
`drop` 释放的是句柄，真正的资源在 GPU 用完之前不会被销毁。

所以那条 `drop` 是**让意图显式**，不是修一个真实的生命周期问题。

### 对实现的影响

辅助函数`**不需要**`把纹理交还出来 —— 返回值保持 `usize` 即可，
纹理随函数作用域结束而 drop，**与提取之前的行为完全一致**。

**我把这条写下来，是为了让下一次实现不要为了一个不存在的问题加复杂度。**
（带 `Vec<wgpu::Texture>` 的返回签名会让调用方多一个 `_keep` 变量，而它什么也不保证。）

## 四、验收判据（真机 GPU）

| 判据 | 为什么是它 |
|---|---|
| **下方被模糊、上方不受影响** | 这就是调整图层的**定义本身** |
| 把调整图层挪到别的位置，受影响范围跟着变 | 防「碰巧通过」 |
| 只有调整图层、下面没有层 → 不崩、不产生内容 | 退化情形 |
| **没有调整图层时结果逐字节不变** | 换路径但行为不变 —— 本仓库反复证明有效的那种判据 |

## 五、风险

| 风险 | 对策 |
|---|---|
| 显存：每帧多两张全尺寸纹理 | 先用现有帧缓存预算兜底；不够再池化。**先把正确性做出来** |
| 多调整图层 | ping-pong 天然支持任意多个；先测 1 个，再补 2 个的用例 |
| 模糊半径上限 | 调整图层的特效同样受 `MAX_RADIUS` 约束，超出走既有报错路径 |
| 与转场冻帧层交互 | 顺序按「已经画上去的」定义，不留含糊；补一条调整图层叠在转场段上的用例 |

## 六、为什么它一直没做（如实记）

它要求**一次性完成**：障碍（compose 的 clear）不先解决就写不对，
而解决它之后又必须把 ping-pong 与「终点落回 target」一起写完 ——
中途停下会留下一个「分段做了但结果不落 target」的状态，**比不做更难解释**。
而每一轮可用余量都不足以覆盖这一段。

**所以这份文件的价值就是：下一轮可以从「实现第三节那三步」开始，而不必重新推演。**
