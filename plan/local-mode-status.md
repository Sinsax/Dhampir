# 本机模式（--local）：收敛结论与证据

> 这是 P4 的一个**子结论**：把「还差什么」和「已经排除了什么」写清楚，
> 免得后来的人（或下一轮的我）从头再猜一遍。

## 结论

**本机模式的浏览器端到端不可用。** 静态模式（默认）不受影响，是当前可用的那条路。

P4 的验收口径据此收窄为：

| 面 | 状态 |
|---|---|
| 降级模式（前端 + 同源静态资源） | ✅ **可用**，里程碑视频产出并经端到端验过 |
| 本机后端的 **HTTP 层** | ✅ **可用**，逐条 curl 验过（工程 / 素材 Range 206 / 能力声明 / 任务生命周期） |
| 本机后端的 **素材与工程解析**（info / gop） | ❌ 未接（要调 Rust 侧分离器，501） |
| 本机模式的**浏览器端到端** | ❌ **不可用**，卡点见下 |

## 卡点（已收窄，未定位到根因）

启动里程碑的回报停在：

    main 进入 -> wasm 已加载 -> 工程文本已取到 -> 工程已解析
    -> 已上屏到 canvas -> 视频源已绑定 -> endFrame 已返回: 90
    （缺「三个面板已渲染」）

即卡在 `endFrame()` 返回之后、`renderTimeline/renderInspector/renderIssues` 之前。

**但这里有一条对我自己结论的怀疑，必须写下来**：那三个是**同步 DOM 函数**，
同步函数不会「挂起」——它要么返回、要么抛。而两种模式下工程内容完全相同，
静态模式跑到同样的位置是好用的。
所以更可能的解释是**观测本身不可靠**（beacon 没刷出、或页面在此处崩掉），
而不是那三个函数真的卡住了。**我把这一点写下来，是为了不让下一个人被这个「卡点」误导。**

## 已经排除的原因（都修掉了，或验证过不是）

| 假设 | 怎么排除的 |
|---|---|
| 驱动自己不退出 | 真原因之一。已修：跑完显式 kill + `unref` |
| 端口被占（EADDRINUSE） | 真原因之一（上一次的残留进程）。已清，并加就绪等待 |
| 后端没就绪就开页面 | 已加 `/health` 等待；未解决 |
| 页面抛 JS 错 | 加了 `window.onerror` + `unhandledrejection` 出口，回报「无」 |
| 跨源被 CORS 拒 | 本机后端已加 `access-control-allow-origin`；未解决 |
| **素材路由不支持 Range** | **真缺陷**，已修（206 + Content-Range），直接 HTTP 验过；**但不是本卡点的原因** |
| seek 无限等 | 排除：`seekVideo` 本来就有 3000ms 兜底 |

## 规律：卡住比失败难查

这几轮的教训不是「某个 API 用错了」，而是**观测顺序错了**：
前四轮（26–29）在「0 帧、无错误、无进展」的不可诊断状态下反复改代码；
真正有用的两步是**先建观测**（页面错误出口 -> 启动里程碑），
它们各自只用了一轮，却把「未知」变成「两个函数之间」。

**下次遇到「什么都没发生」，先建观测，再动代码。**

## 要继续时需要做什么

1. 先确认观测可靠：让页面在 `mark` 里同时把消息写进 `document.title`，
   驱动通过 CDP 或截图读它 —— 绕开 beacon 的刷出时机问题；
2. 再定位：如果确实停在那三个函数，逐个加中间里程碑；
3. 若两轮内仍修不动，就**保持这个收敛结论**，把 P4 的精力移到素材取用契约与 P5 上。
