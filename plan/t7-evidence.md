## T7.1 具名子命令：`undo` / `redo` / `clip` / `sequence` / `batch`

### 「同一实现的糖」到底被什么钉住

这一句验收要求最容易被糊弄过去 —— 只要新写一份"差不多"的实现，也能让所有例子跑通。
所以它被拆成两把**可执行**的尺子：

1. **纯函数那一层**（`cargo test -p dhampir-worker --bin dhampir`）：
   `build_named_op` 拼出来的 `EditOp` 与手写 JSON 解析出来的 `EditOp`
   **逐字段相等**（`assert_eq!` 比的是整个枚举值，不是几个可见字段）。
   同一条路还比了 `undo` / `redo`：`history_alias` 折出来的 `Args` 与
   `edit --undo` / `edit --redo` 解析出来的 `Args` **逐字段相等**。
2. **真跑那一层**（`scripts/check-cli.mjs`）：
   具名写法与等价的 `edit --op` 在**同一个夹具的两份拷贝**上各做一次，
   比**产物字节**与 **stdout 全文**。比"summary 文案对得上"会放过
   缩进、`issues` 顺序、字段缺省值这三类分叉。

两把尺子都在，是因为它们挡的不是同一件事：第 1 把挡"枚举拼错了"，
第 2 把挡"走了一条不同的落盘路径"（比如漏了历史、或写盘顺序反了）。

### 新增的八条契约判据

`scripts/check-cli.mjs` 的 `EXPECTED` 从 22 条加到 30 条：

| 判据 | 问的是什么 |
|---|---|
| `clip-equivalence` | `clip split` 与 `edit --op` 的**产物字节 + stdout** 相同 |
| `sequence-equivalence` | `sequence set` 与 `edit --op` 同上（含 `--timebase` 的有理数换算） |
| `history-alias` | `undo` 与 `edit --undo` 同上 |
| `clip-dry-run` | 不给 `--write` 时 `written=false` 且**文件一个字节没动** |
| `clip-rejects-bad-usage` | 不认识的动作名 / **多给一个开关**都退 2 |
| `batch-matches-edits` | 批处理的结果与**逐条 `edit`** 逐字节相同 |
| `batch-atomic` | 中途一步不成立 → 退 2、**整份不落盘**、summary 里明说**第几行** |
| `batch-empty` | 空脚本（只有注释）→ 退 2 且不动文件（**不是成功**） |

`SUBCOMMANDS` 同步加到 14 个，与 `COMMANDS` 表一致 —— 那条判据本来就是
「加了命令但没登记」与「登记了但 `--help` 没列出来」都要红。

### 三处设计选择，与理由是量出来的

1. **动作名做成第二个位置参数**（`clip split --layer c --at 75`）。
   备选是再来一层 `--op-name split`。选位置参数是因为它更接近 `git`/`ffmpeg` 的习惯，
   而且解析器只需要放宽一处（原先只收一个位置参数）。代价是多了一个 `Args` 字段
   与一段"只有 clip / sequence 收第二个位置参数"的规矩 —— 那条规矩本身有单测。
2. **多给一个开关也报错**，不只是少给。
   少给会被当成"忘了"，多给会被当成"反正不用它" —— 而两者的表现**完全一样**：
   那个值被丢掉，用户以为它生效了。所以每个动作有一张"总共认哪些"的表
   （`op_shape`），多给与少给都退 2，并把人话（`它认的是 …`）打出来。
3. **`batch` 不是"循环调 edit"**。
   若做成宏，中途失败会留下"做了一半"的工程 —— 那既不是改前也不是改后，
   而 `undo` 只能整步退。所以做成**一次写、一条历史**：全成则一次落盘 + 一条历史，
   有一步不成立则**整份不落盘**，并在 summary 与 issues 里带上**行号**
   （"批处理在第 2 行停下"），否则用户只能靠 diff 猜是哪一步。

### 一处自我引入又自我抓到的回归（记下来，因为它是这类改动的典型形状）

把 `--write` 收紧成"只有编辑那一组认"时，漏了 `import` —— 它也要落盘。
表现是 `scripts/check-cli.mjs` 的 `import-write` 当场变红，然后
`library` 与 `import-duplicate` 跟着红（它们依赖上一步真的写进去了）。

修法不是放宽 `--write`，而是**把两张表分开**：

* `EDIT_FAMILY`（6 个）—— 认 `--history` 的；
* `WRITE_FAMILY`（7 个）—— 认 `--write` 的，多一个 `import`。

并把这条钉进单测：`import --write` 必须合法，`import --history` 必须报错。
**合成一张表的代价**正是"顺手把「import 认不认 --history」答成了认"—— 那是错的。

## T7.2（D12）陈旧 wasm pkg：驱动自动重建一次，但"真的坏了仍然红"

### 落点：一个实现，两个用法

`scripts/stale-pkg.mjs` 是**唯一**一份"陈旧判定 + 重建"的实现：

| 谁用 | 用它做什么 | 为什么 |
|---|---|---|
| `scripts/web-check.mjs`（驱动） | 检测到陈旧就**自动重建一次** | 这是 D12 要修的东西：改完 Rust 不该再要求手工重建 |
| `scripts/check-web-invariants.mjs`（守卫） | **只判不修** | 守卫一边判一边改，等于自己把证据擦掉：这次是红的，改完自己变绿，报告就失去意义了 |

两处共用一份实现，是因为"陈旧"的定义（pkg mtime 比源码最新 mtime 旧）必须**只有一个**。

`stale-pkg.mjs` 自检 13 条断言，其中一条专门钉住"注入的 `pkgState` 与真实路径走**同一个**
分支实现"—— 这份仓库明确拒收过"复制一份到自检里"的写法（那测的是复制品）。

### 四把尺子

| 尺子 | 怎么量的 | 结果 |
|---|---|---|
| 陈旧真的会被发现 | 改一个 `.rs` 让源 mtime 超过 pkg | `陈旧: true`，退出码 1 |
| 陈旧能被自动修好 | `node scripts/stale-pkg.mjs --rebuild` | 冷跑 **22.6 s**，重建后 `陈旧: false` |
| **真的坏了仍然红** | 往 `dhampir-wasm` 里塞一个**故意的编译错误**，再走重建 | 退出码 1，报的是**真的编译错误**；pkg 一个字节没动；源码还原后**逐字节相同** |
| 驱动那条路真的接上了 | `node scripts/web-check.mjs --verdict …` | 先自动重建，然后**停在缺后端的检查上退 2**（在 `--verdict` 那条路之前） |

关键在于第三把尺子：**"自动修"最容易退化成"把错也一起吞掉"**。所以专测了
"重建失败时不许假装成功"，并且把 pkg 未被触碰也验了 —— 否则失败会留下半份 pkg，
比原来那个"陈旧"更坏。

### 途中挖出来的一个真问题：失败的 wasm 构建会**毒掉增量缓存**

第一次全量重建成功（22.6 s），**紧接着的第二次重建 ICE 了**：

    error: internal compiler error: ... rustc_metadata/src/rmeta/encoder.rs:2457:
    no entry found for key
    "the compiler unexpectedly panicked"

先用朴素 `wasm-pack build` 复现，再试 `CARGO_INCREMENTAL=0`：

| 跑法 | 结果 |
|---|---|
| 增量（默认） | **ICE**（`encoder.rs:2457: no entry found for key`） |
| `CARGO_INCREMENTAL=0` | **干净通过，9.07 s** |

根因：前面为了证明"真的坏了仍然红"而跑的那次**故意失败的构建**，把
`target/wasm32-unknown-unknown/debug/incremental` 留在了坏状态，于是之后每次重建都崩在
元数据编码上。所以 `stale-pkg.mjs` 的 `rebuildEnv()` **强制 `CARGO_INCREMENTAL=0`**，
并且自检里有一条断言钉住这件事（`env.CARGO_INCREMENTAL === '0'`）。

这条不是洁癖：自动重建一旦 ICE，就会被当成"本机跑不了"，于是回到手工重建——
D12 就白修了。**修一个自动化的毛病，必须连同"它坏起来的样子"一起修掉。**

## T7.3（A9）续渲：**决定不做**，理由与数字

roadmap 给的是两选一（"要么做出可恢复的中间态，要么明确记为不做并说明理由"）。
这里选第二条，并且理由不是"麻烦"，是**量出来的**。

### 先看清楚：这条管道的形状决定了"续渲"只能是什么

出片那条路（`render_plan`，`pipeline.rs:1341`）是一趟**流式**：

    GPU 合成 -> 读回像素 -> 写进 ffmpeg 的 stdin（一帧一次，不落盘）

于是：

* **编码那一段没法续。** MP4 的基本流不能从第二个进程接着写（分片头/索引、以及帧间预测
  的参考状态都对不上）。所以"续渲"最多只能是**别把已经合成过的帧再合成一遍** ——
  也就是一个**逐帧检查点**。
* 而检查点要存的就是**读回来的那 8.29 MB 像素**（1920×1080×4 = 8,294,400 B）。

### 两个候选做法的代价（都是量出来的）

| 候选 | 磁盘（每分钟 1080p30） | CPU | 问题 |
|---|---|---|---|
| 存裸 RGBA | **14.93 GB**（1800 帧 × 8.29 MB） | 本机实测：**写 2343 MB/s = 3.54 ms/帧**，读 2318 MB/s = 3.58 ms/帧 | 磁盘需求荒谬；且检查点必须**保持到出片成功** |
| 存 PNG | 小得多 | 每帧要一次 PNG 编码 | 1080p 的 PNG 编码本身就是十毫秒量级 —— **约等于它想省下的渲染** |

对照：渲染本身实测 **14.56 / 22.50 ms/帧**（T5 的第五、七项），四份不同文件 56.96 ms/帧。

这里有个**本来以为会站在"该做"那边的数**：检查点的 CPU 比我预想的便宜得多
（2.3 GB/s，每帧 3.5 ms，不是几百 MB/s 那种量级）。所以"CPU 太贵"这个理由**不成立**，
我把它划掉了。真正站得住的理由是**磁盘**：一次 1080p30 的一分钟出片要在成功前一直
占着 14.93 GB，十分钟的片子就是 149 GB。这不是"稍微贵一点"，是让出片在普通机器上
直接做不成。

### 那个看起来便宜的设计，其实是一个阶段

"每 N 帧打一个检查点、只重编尾巴"要成立，需要三件互相牵连的改造：

1. 每个检查点**强制一个关键帧**（否则尾巴没法独立编码）—— 会改变成片的码率/画质；
2. 输出改成**分片 MP4**（`+movflags frag_keyframe`）才谈得上"接着写"——
   这会**改产物的字节**，直接撞上 T6 冻结的那条保证
   （`encoder_args` 的 golden argv，以及"无声那条路产物逐字节不变"）；
3. 分片追加的逻辑本身。

这不是"顺手加个开关"，是要重做 T6 已经钉死的那几份证据。**要么整段做，要么不做**，
没有中间档可捡。

### 结论与"什么时候该回来重审"

* A9 -> `wontfix`，理由：**检查点的磁盘代价（8.29 MB/帧）与它省下的计算（14.56~56.96 ms/帧）
  不在一个量级**，而唯一磁盘上可接受的形态（PNG / 分片 MP4）要么把省下的钱花回去，
  要么破坏已经冻结的产物保证。
* 附带风险也记一笔：逐帧缓存**必须**按工程指纹校验（改了工程却命中旧缓存 = **悄悄发出
  一版错的片子**），而且半写完的缓存条目绝不能信（要 tmp+rename+摘要）。这是本仓最怕的
  那类故障（"会悄悄给错东西"），而它换来的只是"重跑少花几十秒"。
* **重审触发条件**（写下来，免得这条变成"永远不做"）：出现下面任一情况就回来重做量化 ——
  ① 出片里**编码**而不是渲染成为主要成本；② 有硬件编码 + 分片 MP4 让"接着写"变便宜；
  ③ 观测到**批量的中途失败**（而不是现在这种"能复现的确定性失败"，那类重跑一次照样同一处红）。

## T7.4（D16）Linux 可移植性守卫

落点：`scripts/check-linux-portability.mjs`。四条规则 + 空集纪律 + 一条交叉声明。

| 规则 | 不许什么 | 为什么这在 Windows 上**永远不会自己变红** |
|---|---|---|
| R1 | 把 `/` 换成 `\`（含正则形式） | 本机就认反斜杠，跑得好好的 |
| R2 | 拿**小写化的整条路径**去访问文件系统 | 本机文件系统不区分大小写 |
| R3 | 假定路径一定是合法 UTF-8 | 本机路径都是合法 UTF-8 |
| R4 | 有 `cfg(windows)` 却没有另一平台分支 | 在 Linux 上那个东西**根本不存在** |

反向是**允许且鼓励**的：`replace('\', '/')`、`.split('\').join('/')` 正是本仓到处在用的
规范化方向（`scripts/record-acceptance.mjs:290` 就是一个），所以它们必须有判据**放过**。

### 尺子

| 尺子 | 结果 |
|---|---|
| 自检 | **21 条断言**全过（每条规则都配了"必须红"的正例与"必须放过"的反例） |
| 真跑 | 扫 **121 个源文件**（75 rs + 46 js/ts），绿 |
| **因写死 Windows 语义而变红**（T7 验收原文） | 见下 |

最后一条是这一段的验收，所以它是**在真树里**验的，不是在自检里：临时放两个探针文件 ——

* `scripts/t7-probe-tmp.mjs`，内容是**格式化器排出来的真实形状** `replace('/', '\')` 加一句
  `.to_str().unwrap()`；
* `crates/dhampir-core/src/t7-probe-tmp.rs`，内容是一个孤立的 `#[cfg(windows)]`。

跑守卫 -> **退出码 1，三条，行号都对**：

    crates/dhampir-core/src/t7-probe-tmp.rs 有 cfg(windows) 却没有另一平台的分支 …
    scripts/t7-probe-tmp.mjs:1 把路径分隔符写成了只有 Windows 认的样子（replace('/','\')）…
    scripts/t7-probe-tmp.mjs:2 假定路径是合法 UTF-8（.to_str().unwrap()）…

删掉探针后**转绿**（121 个文件），`git status` 只剩预期的改动。

### 三处"先量再写"，都是踩出来的

1. **盘符字面量：roadmap 要求禁，量完决定不禁。**
   roadmap 的 D16 第 1 条写的是"不许手写反斜杠**或盘符**"。先量了一遍：
   整棵树有 **12 个文件**含 `C:/…`，几乎全是**正当**的 —— 字体候选表
   （`C:/Windows/Fonts/msyh.ttc`）、Chrome 候选表（**同时还列了 `/usr/bin/google-chrome`**）、
   以及单测里当输入的假路径。禁掉它们会造出一批**假红**，而假红比没有守卫更坏（人会开始无视它）。
   所以这条**明确不实现**，并把理由写在守卫的「这条守卫不管什么」一节里 ——
   验收要求与实现不一致的地方必须写下来，不能默默放过。
2. **R1 必须按"抹掉空白后"的形状比。** 按原样字符串比会**正好漏掉最该抓的那一种**：
   本仓代码都被 prettier / rustfmt 排过，真写错时长的是 `replace('/', '\')`
   （逗号后有空格），而判据原来是 `replace('/','\')`（无空格）。这是手工试写时发现的真窟窿，
   不是想出来的；修法是 `compact()`（抹空白）后再比，顺带把正则形式
   `replace(/\//g, '\')` 也补上。
3. **判据字面量与自检样例必须"拼出来"。** 第一版守卫真跑时红了 **5 条，全是指向它自己**：
   文件头的文档里写着这些形状、规则字面量本身就是这些形状、自检样例也是。
   修法**不是删文档**（删文档就是删守则），也不是把守卫自己排除掉 —— 而是照抄
   `scripts/check-core-purity.mjs` 的现成教训：**注释在判定前抹成空格**（换行保留、行号不变）。
   但**不能连着字符串一起抹** —— 这条守卫的判据本身就以字符串字面量为载体，抹了就全瞎了。
   于是：注释可以随便举例，规则与样例一律拼接，再加一条断言钉死
   "**守卫自己的源码必须判得干净**"。这条断言把"下次顺手直写一行"变成**自检当场红**，
   而不是真跑时冒出一句莫名其妙的"守卫举报自己"。

### 交叉验证：装了 target，所以真跑了（不是"记为不可测"）

roadmap 说"如果能装上 `x86_64-unknown-linux-gnu` 就补一次 `cargo check`；
装不上就如实记为不可测，**不假装跑过**"。实测：**它本来就装着**
（`rustup target list --installed` 里已有），于是这一步真跑了：

    CARGO_INCREMENTAL=0 cargo check --workspace --all-targets --target x86_64-unknown-linux-gnu
    -> Finished `dev` profile in 6.45s（退出码 0）

**但这条绿必须带边界，否则它是虚的**：

| | Linux 目标 | 默认（Windows）目标 |
|---|---|---|
| `dhampir-worker` 依赖图 crate 数 | **116** | **134** |
| ffmpeg / sherpa-onnx / onnxruntime | **不在图里** | 在 |

也就是说原生媒体栈是**平台门控**的。所以这次 check 证明的是
「**我们自己的代码在 Linux cfg 下类型正确**」，
**不**证明"媒体那两条腿在 Linux 上能编、能链、能跑"。这一点不写清楚，
这条绿就会变成一句比没跑更坏的话。

正向对照（"它真的会红"）：往 `crates/dhampir-core/src/lib.rs` 末尾塞一个类型错误再跑，
退出码 **101**、`error[E0308]: mismatched types`，指到那一行；
于是确证这不是一次空跑。源码在**同一个进程里**先读原字节、跑、再写回，
最后断言 `read_bytes() == 原始字节` 为 True —— 不是"应该还原了"，是**验过逐字节相同**。



## T7.5 派生面同步与「守卫总目录」落仓库

### 一个真的交付缺口：守卫清单原来**没交付**

`run-guards` 这份清单原先只活在 `target/t2/run-guards.cjs` —— 而 `target/` 是 gitignore 的。
也就是说「**到底有哪些守卫**」这件事从来没进过仓库：新克隆的人只看到 `scripts/` 下一堆
`check-*.mjs`，不知道哪些算数、哪条要带参数、总共该有几条。

现在它是 `scripts/run-guards.mjs`，三条纪律：

| 纪律 | 为什么必须有 |
|---|---|
| 清单**显式**列出，并与 `scripts/` 实际文件**对表** | 新加一条没登记 -> 红；登记了却不存在 -> 红。**「少一条守卫」永远不会自己变红**，只能靠对表 |
| 对不上就**拒绝继续跑** | 清单不准时，跑出来的"全绿"少跑了守卫，不能当结论用 |
| **fail-closed** | 起不来的（拿不到退出码）算红、不算跳过 —— "跳过"正是守卫消失最常见的形式 |

`--self-test` 4 条用例钉住对表逻辑（一致 / 多出没登记的 / 登记了不存在 / 两边都错）。

### 本会话里的假红：16 / 18，且两条红是**同一个根因**

| 守卫 | 本会话 | 为什么 |
|---|---|---|
| `check-cli.mjs` | **27 / 30** | 红的 3 条（`render` / `render-subtitle-out` / `render-subtitle-out-empty`）都要**真出片** |
| `check-local-backend.mjs` | **16 / 22** | `export-succeeded` 加上它的 5 条下游，报的是 `起不了编码器 ffmpeg：os error 231` |
| `check-dual-end.mjs` | **绿**（最差 SSIM 1.000000） | 它走**逐帧 PNG** 那条路，不碰编码器 stdin |
| 其余 15 条 | 绿 | — |

两条红**不是 9 个独立缺陷**，是同一个根因的下游：本会话的环境**不给子进程开 stdin 管道**。

**对照（这是关键的一行）**：把这条环境限制拿掉之后（沙箱豁免获批的那一次），同一份清单
**18 / 18 条全绿**。所以 **16 / 18 是这个环境的读数，不是仓库的读数** ——
两条红的根因只有一个，而且不在仓库里。

最小复现（纯标准库、无依赖、与本仓代码无关）写在 `scripts/run-guards.mjs` 的文件头：

    stdin=null   -> OK
    stdin=piped  -> ERR os error 231
    stdout=pipe  -> OK          // 注意：**只有 stdin 不行**

已经修掉的两半（都不是"垫片"）：

* **不喂 stdin 的调用**（CLI / ffmpeg / ffprobe）改走 `scripts/spawn-tool.mjs`（`stdin: 'ignore'`）。
  它如实声明"这次调用不喂 stdin"，起不来照样 `status=null`、照样红 ——
  与"给子进程 require 一个改 stdio 的 shim"是两件事，后者会让**真的起不了**也变绿。
  效果可数：`check-cli` 从 **0 / 30**（每一次 spawn 都 EBUSY）回到 **27 / 30**。
* **与判据无关的清理**改走 `scripts/safe-remove.mjs`。本机 CLI 给 `fs.rmSync` 套了一层
  **按 turn 计数**的安全删除（`node-safe-delete-shim.cjs`），而跑一遍套件本身要删掉几百个
  临时路径 —— 于是**越靠后的守卫越容易被"清理"绊倒**。排查时 `check-cli` 一度
  **直接崩在 `collect` 的第一行**，报告上却长得像一条契约不成立，白跑了两趟。
  现在的规矩是：删不掉**只打一行警告**（不静默），**不动退出码** ——
  清理成不成功不该决定一条守卫的结论。

剩下那 3 + 6 条**修不掉**：渲染必须往编码器 stdin 里写帧
（`crates/dhampir-worker/src/pipeline.rs`），那条管道在 JS 这一层够不着。
所以它们在这个会话里就是红的，而且**只应为这一个原因红** —— 换任何一条红都值得停下来查。
要拿真实数字，去**普通终端**（不经 agent 的进程包装）里跑；这一点连同理由都写进了
`scripts/run-guards.mjs` 的文件头，免得下一个人以为是坏代码。

### 一处顺手修的守卫自身缺陷

`run-guards.mjs` 原先对每条守卫只回印**最后 2 行**输出。红的守卫只印 2 行时，
一次 Node 崩溃栈会被截成 `…run_main…` 加一行 `Node.js v22` ——
**恰好把最有用的那行吞掉**。这次就是被它骗过一次。现在红的回印 14 行，绿的仍是 2 行。

同一类修法还有两处，都是"守卫自己的缺陷"，与被测对象无关：

* `check-local-backend.mjs` 在导出没成功时直接拼 `base + status.download_url`，
  拼出 `http://127.0.0.1:8799undefined` 然后抛 `TypeError` —— 崩掉就把
  「到底哪条判据没过」一起吞了。**报告不出来的检查等于没有检查**，现在它把
  `download-url` 缺失这件事按判据报出来。
* `scripts/measure-checkpoint-io.mjs` 用 `statSync(目录).size` 报"落盘占用"，
  而 Windows 上目录项大小恒为 0 —— 于是它**永远印 `0.0 MB`**，一个看着像实测的假数。
  改成逐文件 stat 之后是 497.7 MB，正好等于总字节数（自校验）。顺带发现**写这一项单次波动很大**
  （同参数曾落到 3.54 / 2.98 / 7.23 ms/帧），所以改成跑 3 次取中位数并把极差一起印出来。
