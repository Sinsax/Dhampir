## D1 时间口径

### 决定

**唯一时间基 = 工程文件的 `timebase`（有理数 num/den）。** 两个方向分别定义：

| 方向 | 公式 | 误差 |
|---|---|---|
| **正向**（工程 → WAAPI / HTML 宿主） | `ms = frame * 1000 * den / num` | **精确**（有理数，可精确到 ms 小数） |
| **捕获**（WAAPI → 工程） | `frame = round_half_away(ms * num / (1000 * den))`，中间量用 `i128` | 一次量化，误差 ≤ 半帧 |

三条硬规定：

1. **HTML 宿主的 WAAPI 时长必须由帧数算出来**（正向），**不许反过来**把作者写的 ms 当作真值。
   这样日常开发路径（工程 → 显示）**零误差**，量化只发生在"导入外部动画"这一条路上。
2. **只量化一次**。WAAPI 的 `offset`（0..1）先落到层区间再量化：
   `frame = layer_start + round(offset * layer_frames)`；**禁止**先 `offset → ms` 再 `ms → frame`（两次量化会在长区间上放大误差）。
3. **任何求值路径都不许出现浮点秒**（铁律 1 的延伸）。浮点只允许出现在"转译器的输入端"。

### 量化报告（不静默）

转译器必须输出一份**量化报告**，列入每个被量化的边界及其误差。以下情况**报错，不静默**：

- 误差导致**顺序变化**（两个关键帧被量化到同一帧且先后不可分辨）；
- 误差导致**区间重叠或空隙**（`delay/endDelay` 折算后与相邻段相撞）；
- 误差 > **半帧**（说明源动画的时间分辨率高于工程帧率，应当显式提示作者）。

### 验收

- 单元测试：`30000/1001` 下拿半秒、1 秒、15 帧等控制点对表；
- 反向用例：故意用"两次量化"的写法，必须能测出与正确值不同（证明这条规定有区分度）。

## D2 缓动的表示法

### 决定

**`Keyframe.easing` 从"单元枚举"改为"字符串"，值就是 CSS 缓动语法**，由 `dhampir-timeline` 内一个**零依赖解析器**解析。

值域（缺省 `linear`）：

| 分类 | 取值 | 状态 |
|---|---|---|
| 既有（**原样保留、原样回写**） | `linear` / `ease_in` / `ease_out` / `ease_in_out` / `back_out` | ✅ 不动 |
| CSS 关键字 | `ease` / `ease-in` / `ease-out` / `ease-in-out` / `step-start` / `step-end` | 新增 |
| CSS 函数 | `cubic-bezier(x1,y1,x2,y2)`、`steps(n, position)` | 新增 |
| 暂不支持 | `linear(...)` 断点表 | 报 `unknown_easing` |

校验：解析失败 → 结构化 Issue `unknown_easing`（**不 panic、不静默降级成 linear**——静默降级正是这个项目最要避免的）。

### 为什么选字符串而不是"带参枚举"

1. **与 WAAPI 1:1**：WAAPI 的 `KeyframeEffect.getKeyframes()[i].easing` 与 `getTiming().easing` 本来就是**这些字符串**，转译器不需要做任何翻译。
2. **与本仓既有的哲学一致**：`Effect.kind` 是 `String` + 注册表、`Keyframe.target` 也是 `String`——
   原话是"**加一个特效不该升契约版本**"、"两套表示（枚举 + 字符串）迟早在某一处只认其中一种"。
   缓动用字符串是**第三处同形**，不是新发明的形状。
3. **加缓动不必升版本**：`project_schema` 保持 1（键名与既有取值都不变，只是值域是超集）。

### 代价与影响面（已量）

| 影响面 | 说明 |
|---|---|
| `crates/dhampir-timeline/src/schema.rs` | `Easing` 类型与解析器 |
| `crates/dhampir-timeline/src/curve.rs` | 求值改走 `Easing::parse(..).apply(t)` |
| `crates/dhampir-core/src/compose.rs`、`timeline/edit.rs`、`web/app.js` | 调用点 |
| `fixtures/*.json` | 逐字节不变（既有取值不重写） |
| **3 份生成的 `schema/*.json`** | 要重生成；守卫会抓漂移 |
| `scripts/timeline-contract.mjs` | 契约用例 |

- 解析的**快路径**：先 `match` 关键字（`linear` 等），命中即返回，不分配；
  函数式才走解析。每个关键帧段每帧最多两次解析，量级可忽略。
- **可选优化**（触发条件写在 §重审）：若热点测量显示解析成为开销，再在 `Keyframe` 旁挂一个
  `#[serde(skip)]` 的解析缓存字段。

### 验收

- 每个缓动取若干控制点与浏览器的 `Easing` 逐值比对，**误差 < 1e-6**；
- 两端（wasm / native）调**同一个** `apply`（本仓既有纪律："公式写死在一处"）；
- 老工程逐字节不变（既有 5 个取值原样回写）；
- 反向用例：写入一个非法缓动串，校验必须报 `unknown_easing`。

### 回退方案（不采用，记录备查）

若字符串解析被判定为过重：改为**自定义 serde**——单元变体仍出字符串，带参变体出
`{"cubic_bezier":{"x1":..,"y1":..,"x2":..,"y2":..}}`。代价是**两种形状并存**，
与上面的理由 2 相冲突，所以只在字符串方案被证伪时才启用。

### 实现定版（已落地）

- **Rust 侧形状**：`Easing` 保留单元变体，**新增 `Css(String)` 兜底**；去掉 `derive(Serialize, Deserialize)`
  改**手写** —— 单元变体仍写成 `"linear"` / `"ease_in"` / …（老工程逐字节不变），`Css(s)` 原样写出 `s`。
  **不采用**"把字段类型直接改成 `String`"：那会强迫全仓约 40 处测试构造点改成 `.to_string()`，
  而本文件 §验收 的判据之一是"既有关键帧用例一字不改"。
- **求值**：`Easing::apply(&self, t)` 委派给 `crate::easing`（公式只有一份）；未知串退回线性是**防御性兜底**，
  由校验层的 `unknown_easing` 拦住 —— 与 `Effect.kind` 在热路径 `continue` 是同一套哲学。
- **校验落点（两处）**：`validate_project_doc`（project.rs 的 keyframe 循环）与
  `validate_project_with_effects`（schema.rs 的 v1 clip 循环）。注意 `validate_timeline_v2` **不遍历 keyframes**，放不了那儿。

### 派生物的代价（实测，**需要一次决定**）

`schemars` 按 Rust 形状派生，所以 `Css(String)` 会被派生成一个**对象**分支。定版做法是在字段上加
`#[cfg_attr(feature = "json-schema", schemars(with = "String"))]` → JSON Schema 变成
`{"type":"string","default":"linear"}`（与"JSON 里就是字符串"这条口径一致）。

**代价**：`scripts/timeline-contract.mjs` 的 `tsType` 把 `{"type":"string"}` 翻成 `string`，
于是 `schema/*.d.ts` 里 `easing?: Easing` 退化成 `easing?: string` —— **五个既有字面量在 TS 侧没了**
（改动前是 `export type Easing = "linear" | … | "back_out"`）。生成器里那句注释正是为这种事写的：
"少了这一支…约束在 TS 侧就没了（`TrackKind` 上真实发生过）"。

| | 做法 | 代价 |
|---|---|---|
| **A** | 接受 `string` | 下游 TS 失去自动补全；但与本仓既有的开放串一致（`Effect.kind`、`Keyframe.target` 本来就是 `string`） |
| **B（倾向）** | 给生成器加一条**开放串**成例：schema 出 `anyOf:[{enum:[…5]},{type:"string"}]`，`tsType` 在"字面量 + string"的并集上输出 `"linear" | … | (string & {})` | 要动生成器 + 三份派生物，并给它补一条判据（生成器本身是守卫） |
| **C** | 手写 `impl schemars::JsonSchema for Easing` 出裸字符串 | TS 结果同 A，只多一段手写代码 |

B 的收益不只缓动：`Effect.kind` / `TransitionSpec.kind` / `Keyframe.target` 三处开放串现在也是 `string`，
同一条成例可以一起受益。

**已定：走 B**（2026 这一轮落地，读数如下）。实现比原计划更省一层 —— 不需要动 `schemars` 的派生形状，
也不要手写 `JsonSchema`：schema 仍是裸 `{"type":"string","default":"linear"}`，
**另外带一个扩展键** `x-known-values`（五个既有拼写），由 Rust 侧的
`#[schemars(extend("x-known-values" = [...]))]` 给出；生成器的 `tsType` 见到它就产出
`"linear" | … | (string & {})`。

```ts
// schema/timeline-v4.d.ts（重生成之后）
easing?: "linear" | "ease_in" | "ease_out" | "ease_in_out" | "back_out" | (string & {});
```

**真值仍在 Rust 侧**（那个 `extend` 就写在 `Keyframe.easing` 的字段属性上、紧挨着 `Easing` 枚举），
生成器只负责翻译 —— 这是选 B 而不是"在 JS 里维护一张表"的原因。

**判据**：`scripts/timeline-contract.mjs --self-test` 里两条新断言
（开放串带上已知取值 / 没有已知取值的串还是 string）；再加上它原有的**逐字节**比对 ——
`node scripts/timeline-contract.mjs` 重新推导一遍，与仓库里那三份不一致就红。

**收益面**：`Effect.kind` / `TransitionSpec.kind` / `Keyframe.target` 三处开放串将来想要补全，
只要在各自的字段上加同一个 `extend` 即可 —— 成例已经就位并有判据。

## D3 `iterations / direction / fill`

WAAPI 的 `getTiming()` 给 8 个量。处置：

| WAAPI 字段 | 处置 | 理由 |
|---|---|---|
| `delay` | **用层区间吸收**（`start` 前移/后移） | 零契约改动，语义无损 |
| `endDelay` | **用层区间吸收**（`end`） | 同上 |
| `fill`（`forwards`/`backwards`/`both`/`none`） | **用层区间吸收**（延长 `end` / 前移 `start`） | 同上；"保持末值"等价于"把层延长" |
| `iterations` | 第一版**展平**，门槛 `≤ 64` | 见下 |
| `direction` | 第一版**展平**（`alternate` 要反向复制键序列） | 见下 |
| `iterationStart` | 第一版**只支持整数**；非整数报不支持 | 非整数相位会引入额外量化误差 |
| `duration` | 映射成"关键帧序列跨越的帧数" | 已有概念 |
| `easing` | 见 D2 | — |

**展平规则**：`direction=alternate` 时，第 k 遍的键序列按 `first + mirror(keys)` 生成；
`alternate-reverse` 从反向起；每次复制**只量化一次**（在生成绝对帧号那一步）。

**门槛与"明确不做"**：`iterations > 64`（含 `Infinity`）或 `iterationStart` 非整数 → **明确报不支持**，
不做静默近似。`Infinity` 的处理：提示"用层的 `end` 截断等价表达"。

### 契约扩展候选（记录，不在第一版做）

若"循环动效成为常态"或"展平后文件明显膨胀"，则按 **WAAPI 的形状**引入：
**每个 `target` 一个"通道"（keyframes + timing）**，而不是继续在层上加字段。
重审触发条件：

1. 展平后单工程关键帧数超过某个阈值（测量后再定）；
2. 需要 `iterationStart` 的非整数相位；
3. 需要 `Infinity` 的闭式循环。

> 之所以现在不做：本仓现在**没有 tween 对象**（关键帧直接挂在层上、多 target 共存），
> 按 WAAPI 形状补通道是一次**结构级**改动（要升 `project_schema`）。第一版的目标是
> "把链跑通"，不是"一步到位"。

## D5 CSS 滤镜口径（量出来的，不是拍的）

**背景**：能力登记表里 `filter.blur` 原先标着「用之前先量」—— CSS 的 `blur(R)` 与本仓的
`gaussian_blur` **不同源**，谁都不会报错，只会看着「差一档糊」。

**量出来的事实**（`crates/dhampir-core/src/render/blur.rs`）：

| | 口径 |
|---|---|
| 本仓 | `sigma = radius / 2`（核覆盖 ±2σ）；权重在 Rust 里算一次、打包进 uniform（**核只有一份来源**） |
| CSS | `blur(R)` 的参数**就是标准差**（Filter Effects 规范） |

**所以口径是：`radius = 2 × R`（同一像素空间）。** 写反不会报任何错，只是在两端差一档糊 ——
所以它必须被**钉住**，而不是写在注释里。

**判据**：`render::blur` 的测试 `css_的_blur_是本仓半径的两倍` —— 用权重之比
`w[1]/w[0] = exp(-1/(2σ²))` 直接钉 σ。
**反向验证过**：把实现里的 σ 从 `radius/2` 改成 `radius`，这条立刻红（`test result: FAILED`）；
还原后文件哈希与变异前一致、测试恢复绿。

**上界**：`radius ≤ BLUR_MAX_RADIUS(16)` ⇒ **CSS σ 上界 8**（1:1 时）。更大的模糊要加抽头，
而抽头数是禁循环的定长展开 —— 这就是「想支持更大的 blur 要付什么」的答案。

**还没钉的一半**（写下来，免得当成做完了）：**转译器侧还没有滤镜**（`waapi2doc` 这一版只做
transform / opacity），所以「把 CSS 的 R 乘 2 写进工程」这一步目前没有判据。
转译器学会滤镜时，必须在**同一次改动**里补一条（例如：给一条 `filter: blur(4px)` 的样本，
断言产出的 radius 是 8）。

## D6 CSS 滤镜口径（色彩部分，量出来的）

**背景**：登记表原先把四条色彩滤镜合成一条 `filter.color`，但它们的判定**并不一样** —— 查下来只有一条逐值等价，
另有一条**不等价**、一条矩阵不同源。合成一条就看不见这个差别，所以这一轮拆成四条
（`filter.contrast` / `filter.saturation` / `filter.brightness` / `filter.hue-rotate`）。

**CSS ↔ 本仓 对照表**

| CSS | 本仓 | 映射 | 等价性 |
|---|---|---|---|
| `contrast(k%)` | `contrast{amount}` ∈ [0,4] | `amount = k` | **等价**：两边都是 `(c−0.5)·a + 0.5` |
| `saturate(k%)` | `saturation{amount}` ∈ [0,4] | `amount = k` | **几乎等价**：本仓 luma 用 Rec.709（0.2126/0.7152/0.0722），CSS 规范那组写成 0.213/0.715/0.072 —— 第 4 位起不同 |
| `brightness(k%)` | `brightness{amount}` ∈ [−1,1] | `amount = k − 1` | **不等价**：CSS 是**乘**（`c·k`，黑仍是黑），本仓是**加**（`c + a`，黑被抬亮、亮部截断） |
| `hue-rotate(Ddeg)` | `hue{degrees}` ∈ [−180,180] | `degrees = D` | **角度一致、矩阵不同源**：本仓用 YIQ / Rec.601（0.299/0.587/0.114）那套经典旋转矩阵；SVG/CSS 规范用 0.213/0.715/0.072 与另一组 sin 系数 |

**引擎侧已经钉住的**（真值在那边，上表只是翻译）：

- 恒等值 brightness 0 / contrast 1 / saturation 1 / hue 0 —— `render::timeline` 的测试 `四个恒等特效折出来仍然是恒等`；
- 叠加语义（亮度加、其余乘，**顺序无关**）—— `同类色彩特效叠加是可交换的`；
- **度转弧度只在折叠时发生一次**（所以转译器填的是**度**）—— `度转弧度在折叠时发生且只发生一次`；
- 公式本体只有一份：`crates/dhampir-core/src/shaders/color_adjust.wgsl`。

**要真等价得付什么**（三条都是「新增」，不是「改」）：

1. **brightness**：加一条**乘性**亮度。**不能改**现有 `brightness` —— 改了老工程出片就变，
   而「老工程逐字节不变」是本仓的硬判据。
2. **hue**：加一条按 SVG/CSS 规范矩阵的色相旋转；同样只能是新增。
   **与浏览器的差异登记在 `scripts/dom-parity-differences.toml` 的 `filter.saturation_luma_rounding`**（未实测）。
3. **saturation**：要么把 Rec.709 的常数按规范那一组取整（会动现有输出 → 也得新增），
   要么**接受这处微小差异并写进容差**。

**还没钉的一半**：转译器这一版还没有滤镜，所以上表那几行映射目前**没有判据**。
转译器学会滤镜时必须在同一次改动里补判据 —— 至少要有：`contrast(200%)` → `amount 2.0`、
`brightness(50%)` → `amount −0.5`（**不是** 0.5）、`hue-rotate(90deg)` → `degrees 90`。

### 转译器侧（第 15 轮补上的一笔债）

D5 / D6 / D9 / D10 都写了同一句话：「**转译器这一侧还没有滤镜 / 混合 / 圆角**，学会时必须在同一次改动里补判据」。
这一轮补上了 —— `scripts/waapi2doc.mjs` 现在的规矩是：

| 快照里写什么 | 转成什么 | 口径 |
|---|---|---|
| `filter: blur(Rpx)` | `gaussian_blur { radius = 2R }` | D5（CSS 的 blur 参数就是 σ） |
| `filter: contrast(k)` | `contrast { amount = k }` | D6（同一个公式，逐值等价） |
| `filter: saturate(k)` | `saturation { amount = k }` | D6（**近似**，报告里带台账条目名） |
| `filter: brightness(k)` / `hue-rotate(D)` | **跳过整条动画并说明理由** | D6（乘 vs 加 / 矩阵不同源） |
| 关键帧里的 `filter`（**只有参数在变**） | 特效 + `effect.<i>.<param>` 通道 | 第 18 轮接上；关键帧之间**函数列表变了**就明说跳过 |

| `border-radius: Rpx` | `corner_radius`（只支持单一半径，四角各写一个就明说） | D10 |

判据在 `scripts/check-waapi2doc.mjs`：既定答案（card 层的三条特效 + overlay + 圆角 12）、
「引擎还没实现」的警告必须出现、近似必须带**可引用的台账条目名**、自检 **14** 个变异全红。
其中一条跨文件比对盯着「引擎实现了哪几条混合模式」在 `layer.rs` / `web/dom-css.mjs` / 转译器三处**必须一致**。

**第 18 轮又发现一件同类的事**：`effect.<i>.<param>` 这条通道**引擎一直有**（`compose.rs` 用它覆盖特效参数，
`project.rs` 还校验下标与参数名），而**转译器之前遇到关键帧驱动的滤镜就整条跳过** —— 那是转译器的锅，
不是引擎的缺口。修的过程中，判据自己又拦了一次：它那条"关键帧 target 必须在五个固定通道里"的规则**太窄**，
把契约本来就支持的 `effect.<i>.<param>` 挡在外面。现在这条规则改强了 —— 不只放行，还顺带校验
**下标存在**与**参数名存在**（各自一条自检变异盯着）。

**一个值得记下的发现**：样本里 card 用了 `overlay`（引擎未实现），而端到端出片**没有报错** ——
因为那一层没有素材、根本走不到绘制那一步（第 12 轮查圆角拒绝时踩过同一个坑）。
这正是「契约与校验层才是唯一能看见占位层的地方」的实证：警告在转译期就发出来了，
而渲染前的那道拒绝只对真正要画的层生效。

## D11 裁剪形状：只做「每像素一个覆盖度」能表达的三种

**做了什么**：契约加 `Layer.clip`（`kind` 标签三态：`circle` / `ellipse` / `inset`，长度一律**文档像素**，
`center` 缺省 = 图层中心），引擎在合成着色器里用一组**无分支** SDF 画它，DOM 侧用 CSS `clip-path`。

**为什么只有这三种**：引擎的覆盖度是每像素算出来的，能用同一套式子表达的只有圆 / 椭圆 / 圆角矩形 ——
正好是 CSS 的 `circle()` / `ellipse()` / `inset()`。`polygon()` / `path()` 要一般多边形求交或矢量渲染器，
**明确不做**（登记表里单列成 `explicitly-not-doing`，并写明「真要做，先走掩码纹理那条路」）。

**三个技术要点**（都是查过或踩过才知道的）：

1. **椭圆用的是「把圆按半径归一化」那个近似**：`(length(p / radii) − 1) × min(rx, ry)`。
   **零集精确**（内外判定没错），远处距离值不精确 —— 而距离只用在做抗锯齿的那一圈，够用。
   判据里专门放了一个**判别点**：椭圆在 y 轴 `(rx+ry)/2` 处必须透明；若把它画成半径 `rx` 的圆，那里会是红的。
2. **`select` 两支都会求值**：所以「没有裁剪」时 Rust 侧给的是**安全占位值**（半径 1、半宽 1）而不是 0 ——
   否则未选中那一支会算出 `0/0`，而 `NaN` 一旦进了乘法，`mix(1, NaN, 0)` 仍然是 NaN，
   「没有裁剪时逐字节不变」就毁了。
3. **与圆角同时生效**：两个覆盖度**相乘**，与 CSS 里 `border-radius` 与 `clip-path` 同时写的行为一致。

**判据**（一个都不是「看着对」）：

- 契约往返：缺省不写进文件；居中不写 `center`；内缩的圆角为 0 不写 `radius`；
- **没有裁剪时出片 sha256 与基线一字不差**（`8b7d9e18a7320ee7`）；
- GPU 用例「裁剪形状_圆与椭圆与内缩矩形各切对地方」：圆 → 四角**与四条边中点**都透明
  （圆角只切四角，这就是两者判别点）；椭圆 → 在/不在的点 + 上面那个判别点；内缩 → 边界一圈透明、往里 5 像素仍红；
- DOM 侧：三种形状的 CSS 拼写逐字符串钉住，`polygon` **必须被拒绝**；宿主接线里第五层的 `clip-path` 必须是 `circle(8px)`；
- 允许表：没有新构造（`min(` 上一轮已申报），普查 40 条全申报。

### 第 22 轮：DOM 侧那条"刻意不设"的规矩

掩码在 CSS 里有个**会咬人的语义**：**遮罩图取不到 = 全黑 = alpha 0 ⇒ 整个元素被遮没**。
而本仓工程里的 `asset.uri` 常常只是**相对文件名**（`m.png`），DOM 宿主没有它的基准路径 ——
照写 `url(m.png)` 的话，预览里那一层会**整个消失**，那比"画不出掩码"坏得多。

所以 DOM 侧分两种：

- uri 是**能直接取的**（`http:` / `https:` / `blob:` / `data:`）→ 写 `mask-image`，并标**未实测**（这一版不做素材解码）；
- 否则 → **不设**，并**报出来**（"不设"是刻意的，不是漏了）。

判据把这条当**主断言**（不是在测拼串）：`checkMaskCases` 里"取不到时**不该设**"那一条，加上自检里那个
"不管取不取得到都写 `url`"的错误映射器 —— 后者会**把元素遮没**，是这类代码最容易犯的错。

差异登记在 `scripts/dom-parity-differences.toml` 的 `mask.sampling_and_availability`（未实测）：
能不能取到素材、掩码内部的插值核不同、以及**反相在 CSS 的 `mask-image` 里表达不了**（这一版没画上去）。

### 第 24 轮：`polygon()` 从「明确不做」变成可做 —— 用的就是本节写下的那条路

本节第一条就写着「`polygon()` / `path()` 要一般多边形求交或掩码纹理」。掩码纹理在第 21–23 轮打通之后，
多边形就只剩**栅格化**这一步了：

- 栅格化器落在 **core**（`render/polygon.rs`，纯 Rust、零 `#[cfg]`）—— 两宿主共用同一份代码，
  这是「预览所见 = 成片所得」在几何上的又一处兑现；
- 栅格化结果是**一张掩码纹理**，所以**着色器一行都没改**（复用已经 GPU 验过的那条通路）；
- 口径：顶点是**图层框内的归一化坐标**（与圆/椭圆的 `center` 同一套）、**非零环绕**、
  像素中心采样 + **2×2 超采样**近似抗锯齿；
- 两条契约层口径：顶点少于 3 个 → `clip_polygon_too_few_points`（少了它整层会被裁掉，
  那不是作者想要的）；**与掩码同时给 → `clip_polygon_with_mask`**（两者都要占那条通路，
  **明说不支持**，不替作者挑一个用）。

判据：栅格化器 6 条单测（含 L 形凹口与绕向无关）+ GPU 用例「多边形裁剪只留下三角形那一半」+ DOM 的百分比拼写。

> 记一笔自己的错：这条 GPU 用例我第一版把方向想反了 —— 归一化 `(0,0)` 是**左上角**（y 向下），
> 所以 `[0,0] [1,0] [0,1]` 盖住的是 x+y ≤ 1 的**左上那一半**，而我按"左下"写的断言。
> 这是同一类错第二次（第 21 轮是把 2×2 掩码的采样点想当然）。**几何断言必须先把轴向写下来再写数。**

### 第 25 轮：`path()` 也进来了（同一套通路，只多一步细分）

- 细分器（SVG `d` → 折线）落在 **`dhampir-timeline`**（纯数据、无 GPU 依赖）—— 这样**校验层与渲染层
  用同一份解析**：路径读不出来时 `probe` 就能报 `clip_path_unparsable`，而不是等到渲染才炸；
- 支持 `M L H V C Q Z`（含小写相对形式）；**第 26 轮补齐了弧 `A` 与光滑续接 `S` / `T`**：
  弧按 SVG 规范 F.6.5 的**端点参数化 → 圆心参数化**（含"半径不够大就按规范放大"那一步 ——
  不做的话圆心解出 NaN，表现是"这个形状整个不见了"，很难查），再按固定 24 段采样；
  `S`/`T` 是**控制点镜像**，有"与显式写出完全一致"的等价性单测钉着；
  仍然认不出的命令**报错点名**，不猜近似；
- 曲线按**固定段数**细分（三次 16 段、二次 8 段）：确定性优先 —— 自适应细分会让两端算出的折线不完全一样；
- 坐标口径：**文档像素、原点在图层框左上角**（与 CSS `path()` 同一套，所以 DOM 侧**原样透传**）；
  引擎按图层框的文档像素尺寸（`source_size × scale`）归一化后再栅格化。

判据：细分器 8 条单测（相对命令 / 隐式重复 / 不支持命令 / 指数与贴在一起的数字）+ GPU 用例
「路径裁剪的直线与曲线都对」（曲线那两条断言是**从曲线方程算出来的**：`M 0 0 C 0 32 32 32 32 0 Z`
的中点在下边界 (16,24)，所以 (16,16) 在内、(16,30) 在外）。

### 第 37 轮：`linear()` 断点表也支持了

CSS `linear()` 曾是本仓**唯一明确说"不做"**的缓动形式（解析器里那条 `Unsupported`）。第 37 轮补上：

- `EasingForm::LinearStops { stops: Vec<(f32, f32)> }` —— 位置按规范那三条补全
  （只写值的均匀铺开、首个缺省 0%、末个缺省 100%）
- **值允许过冲**（`linear(0, 1.2 50%, 1)` 合法），所以只校验**位置**：非递减、在 0..100% 内
- 位置相等按规范取**后一个**的值（那就是"瞬跳"该有的行为）
- **`EasingForm` 因此不再是 `Copy`**（它带 `Vec`）—— `apply` 从 `match *self` 改成借用匹配
- 判据：3 条单测（手算期望值：`1/6`、`0.625` 处 `0.5`、过冲 `1.2`）+ 浏览器参照用例 3 条
  （在 `scripts/easing-reference.mjs`，用户跑一次就能把"三处算的是同一条折线"钉死）

**还没做的**：`clip-path` 的**转译器侧**（从 WAAPI 快照里读 `clip-path:`）还没接 ——
登记表那条能力里写明了这一点。它与第 15 轮补滤镜是同一笔账：**先在网页侧与引擎侧打通，再补作者侧**。

### 第 17 轮：转译器侧补上，并且**改了一次契约口径**

| 快照里写什么 | 转成什么 | 备注 |
|---|---|---|
| `circle(40px)` / `circle(40px at 25% 75%)` | `{kind: circle, radius: 40, center?: [0.25, 0.75]}` | `at 50% 50%`（或不写）→ 不写 `center` |
| `ellipse(30px 20px)` | `{kind: ellipse, radius_x, radius_y, center?}` | 同上 |
| `inset(10px 20px round 4px)` | `{top: 10, right: 20, bottom: 10, left: 20, radius: 4}` | **按 CSS 规范展开简写**（1/2/3/4 个值各一套规则） |
| `polygon()` / `path()` / `url()` | **跳过整条动画并说明理由** | D11 明确不做 |
| `circle(50%)`（百分比半径） | **跳过** | 半径要文档像素 —— 转译器不知道图层尺寸 |
| `at 10px`（像素位置） | **跳过** | 位置要百分比（归一化） |

**改了一次契约口径**（这一步是被转译器逼出来的）：上一轮我把 `center` 定义成「相对图层中心的
**像素偏移**」，而 CSS 的 `at X Y` 是相对元素**左上角**、只有 `X%` 才是相对尺寸的 —— 于是转译器
必须知道图层的像素尺寸才能换算，而它**不可能知道**（尺寸是素材的属性）。

改成**归一化比例**（`[0.5, 0.5]` = 正中，`None` 等价于居中）之后：作者侧 `at 25% 75%` 原样进工程、
DOM 侧原样转回 `at 25% 75%`（同一个口径），而像素值仍然拒绝 ——
**需要尺寸才能换算的东西，就该在需要尺寸的那一层拒绝**。

GPU 用例里补了一条判别断言：圆心挪到宽度的 1/4 处后，**原来的正中必须变透明**
（若按旧口径把它当像素偏移，这两条会正好反过来）。

## D7 方向 = 镜像（`direction` 怎么进底座）

**结论**：方向**不进契约** —— 它是转译期的事。反向的那一遍把**值序倒过来**，
并把每一段的缓动换成它的**镜像**：

```
E′(u) = 1 − E(1 − u)
```

来历：正向段是 `value(u) = v_i + (v_{i+1}−v_i)·E(u)`；倒着走时 u → 1−u，
把它改写成「从 v_{i+1} 到 v_i 的段」时，缓动就必须是上面这条。

**为什么这不是近似**：对**可镜像的**缓动，这是逐值相等的改写；`alternate` 的交界处首尾值天然相同，
所以两遍合并成一个键毫无损。不可镜像的那些**明说不支持**，不近似。

**可镜像性表**（`mirrorEasing` 的全部知识）：

| 原 | 镜像 | |
|---|---|---|
| `linear` | `linear` | ✅ |
| `ease_in` ⇄ `ease_out`、`ease_in_out` | 同类（二次曲线一族自洽） | ✅ |
| CSS 关键字 / `cubic-bezier(x1,y1,x2,y2)` | `cubic-bezier(1−x2, 1−y2, 1−x1, 1−y1)` | ✅ |
| `steps(n, jump-end)` ⇄ `steps(n, jump-start)`、`step-start` ⇄ `step-end` | 同类 | ✅ |
| `back_out` | 需要 `back_in` —— **本仓没有** | ❌ 明说 |
| `steps(n, jump-none / jump-both)` | 镜像后不是那四个跳跃位置里的任何一个 | ❌ 明说 |

**一条曾经的"硬墙" —— 第 48 轮更正：它不是墙。**

原先的判断是：`normal`/`reverse` 且 `iterations > 1` 时，交界帧上「前一遍的末值」与「后一遍的首值」
撞在同一帧，而"一个键只有一个 easing"，所以表达不了 ⇒ 明说不支持。

**这个推理漏了一步**："交界帧本身放不下两个值"是对的，但**正确的表达不需要把它们挤在同一帧**。

- CSS 的迭代是**半开区间** `[kB, (k+1)B)` ⇒ 第 `B` 帧取的是**后一遍**的首值；
- 而本仓只在**整数帧**求值（铁律）⇒ 只要在 `B−1` 补一个键、值取**前一遍在那一帧的值**，
  **逐整数帧的取值就与 CSS 完全一致**（`B−1` 属于前一遍 ✓、`B` 属于后一遍 ✓）；
- 那个补出来的键带着 `B−1 → B` 这一段的"一帧缓动"；这一段内的取值**永远不会被求值**
  （求值只发生在整数帧）⇒ 它的 easing 取什么**都无害** —— 这正是原推理把它当成障碍的地方。

所以这条是**可精确表达**的，成本只有"在交界前一帧采样一次"（缓动的值是确定的、可精算）。
**本轮先不改行为**：继续拒绝 —— 过拒绝是响亮的、安全的；实现与判据留下一步。

> 记这条更正的理由：它和 D13 第 30 轮那次一样，是"**当初的推理少了一步**"，而不是"世界不允许"。
> 本仓的规矩正是让这类推理**写下来可复核** —— 写下来之后，它就被复核出错了。

**第 49 轮的二阶更正：上面那条更正**只对了一半**。**

"在 `B−1` 补一个键"能让**交界那两帧**对，但会让**整段内部的帧**偏掉 —— 因为键的 easing 描述的是
"从这个键到下一个键的整段"，把段尾从 `B` 移到 `B−1` 之后，**段的长度变了、easing 没变**：

```text
通道：authored 两个键 progress 0→1、值 0→1、段缓动 E（比如 ease-in），span = 12 帧、iterations = 2、direction = normal。

CSS 在第 1 遍第 f 帧的值：v(f) = E(f / 12)                ← 分母是**一遍的长度**
补救后本仓在第 f 帧的值：v′(f) = E(f / 11)（段尾挪到 11）  ← 分母变成了 11
   两者只在 f = 0 与 f = 11 相等；f = 6 时就差得出来（E(0.5) vs E(0.545)）。
```

**所以精确表达它需要的不只是"多一个键"，而是把这一遍的键按整数帧**烘开**（每个整数帧一个键）。**
那是对的（整数帧铁律下逐帧精确），代价是文档里这一条通道的键数按遍长增长 —— 12 帧的动画、

文档里多 11 个键。要不要付这个代价是**产品决定**，不是技术决定，所以这一轮我**不改行为**：
继续明说不支持（响亮、安全），把代价写清楚留给决定。


### D7 的取舍：**其实有三个选项，不是一个**（第 70 轮补）

这条一直挂着"等决定"。决策前先把**代价算出来**（数字来自真实键体积 ≈ 60 字节/键，
键数按 `iterations × span + 1` 算 —— 都是可复核的算术，不是感觉）：

| 情形 | 现状（展开成每遍的关键帧） | 烘帧（每个整数帧一个键） | 增量 |
|---|---|---|---|
| `badge`（3 遍 × 12 帧，1 通道） | 4 个键 | 37 个键 | **+825%**，约 +1.9 KB |
| 中等（2 秒、5 通道） | 20 个键 | 905 个键 | 约 **+52 KB** |
| 长（10 秒、8 通道） | 24 个键 | 4808 个键 | 约 **+280 KB** |

**三个选项：**

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A 烘帧** | 转译器把那一遍按整数帧烘开（本轮之前一直在讨论的） | 与 CSS **逐帧一致**（整数帧铁律下精确） | 上表的体积，**永久留在每个用到的工程文件里**；而且只解决"同向重播首尾不同"这一种情形 |
| **B 现状（明说不支持）** | 转译器拒绝并说明理由 | 响亮、安全；**文件里不多一个字节** | 作者得自己把那条动画拆成两段（**成本在作者侧、一次性**） |
| **C 契约里加 `iterations`/`direction`** | 让**引擎**原生求值迭代与方向（像 CSS 那样） | 最干净：**没有烘帧的体积、也没有作者的工作量**；且 `iterationStart` 的非整数相位也一起解决 | 是契约 + 求值 + 两侧宿主的一次**结构性改动**（比 A/B 都大） |

**我的建议是 B，理由是把代价放在哪一侧：**

- A 把代价放在**产物**里（每个工程文件永久变大，且只在极少数情形下需要）；
- B 把代价放在**作者**侧（拆一次，一次性）；
- C 才是真正的解，但它不该被夹在"这条要不要做"里讨论 —— 它是**另一件事**（D2/D14 那一条线上该做的事）。

所以：**现在保持 B**（明说不支持、理由带具体值）；等哪天真有作者需要同向重播的跳变、且不愿拆，再把 C 提上日程。
这个结论**不需要你现在拍板** —— 它只是把"什么时候该翻案"写清楚：出现第一个"不愿意拆两段"的真实需求时。
> 记这条二阶更正的理由：第 48 轮我"证明了墙不存在"，但那个证明**自己少了一步**（段的长度会变）。

> 写下来的推理被复核出两次错 —— 这正是把它写下来的价值。**没有写下来的推理，两次都不会被发现。**


**判据**（都不是看着对）：

- `check-waapi2doc` 的**既定答案**：样本里 `badge`（iterations=3 + alternate，源 easing `ease_in`）
  必须产出 `0=0.3(linear) | 12=1(ease_in) | 24=0.3(ease_out) | 36=1(ease_in)`，且层长 `= 3×12+1 = 37`；
- 两条自检变异必红：「镜像后的缓动被抹平成线性」「层长没按遍数算」；
- `sparkle`（`back_out` + alternate）必须在报告里带 `back_out` 的跳过理由。

**顺手修掉的一个静默少渲染**：早期版本的 `waapi2doc` 只展开**一遍**（`iterations>1` 时层长仍按一遍算）。
样本里唯一的多遍动画当时因为 `alternate` 被整条跳过，所以这个错**从没被触发过** ——
这正是「让能力长起来」的副作用：以前被跳过的东西，一旦真的转起来，藏在下面的错就露出来了。

## D8 能力迁移的搬运规则（DOM 侧实操）

**这一步做了什么**：DOM 宿主从「只会画 transform / opacity 的方块」变成**也能画特效** ——
但它**不是**把 CSS 有什么就用什么，而是按 D5 / D6 的口径**只搬能证明等价的**。

| 本仓特效 | DOM 侧 | 为什么 |
|---|---|---|
| `contrast{amount}` | `contrast(amount)` | 逐值等价（同一个公式） |
| `gaussian_blur{radius}` | `blur(radius/2 px)` | 逐值等价（D5：CSS 的 blur 参数就是 σ，本仓 σ = radius/2） |
| `saturation{amount}` | `saturate(amount)` + **近似说明** | 几乎等价（luma 权重取整不同，见 D6）—— 应用它，但**带着理由报出来** |
| `brightness{amount}` | **拒绝** | 本仓是加、CSS 是乘（D6）—— 差得不小 |
| `hue{degrees}` | **拒绝** | 旋转矩阵不同源（D6） |
| 其余（drop-shadow / mask / …） | **拒绝** | DOM 宿主还没实现 |

**两条规矩**（这才是有判据的部分）：

1. **只搬能证明等价的**。搬之前先问「这两边画出来是不是同一个东西」，而不是「CSS 有没有这个函数」。
2. **拒绝必须报出来**。页面上会显示「这几条 DOM 侧画不出来，原因是……」——
   静默画一个「看起来差不多」的东西比画不出来更坏：前者让人以为预览是对的。

**判据**：`scripts/check-dom-css.mjs`（已登记进 `run-guards.mjs`）

- `checkCases`：逐条钉映射（含 `blur(4px)` 而**不是** `blur(8px)`；亮度与色相必须被拒绝，理由要点到「乘」与「矩阵」）；
- `checkHostWiring`：用**最小 DOM 替身**验宿主接线 —— 第一层的 `style.filter` 必须是 `contrast(2) blur(4px)`，
  第二层（两条都被拒）必须是空串，且那两条拒绝要出现在回报里；
- `--self-test`：拿**两个看起来很合理的错误映射器**（把亮度天真地搬成 CSS brightness、模糊忘了 σ = radius/2）
  跑同一套用例，必须红。

**一句实话**：`checkHostWiring` 用的是替身，验的是**接线**（属性有没有写上），**不是渲染**。
真渲染仍然要浏览器 —— 那一条仍然挂在阶段 3 的出口上。

## D9 混合模式：预览能画 9/9，引擎只实现 4/9

**这是「阶段 4 形态」第一次真的出现**：DOM 宿主画得出来，而引擎画不出来。

| 本仓 `BlendMode` | CSS `mix-blend-mode` | 引擎 |
|---|---|---|
| normal | （不设样式） | ✅ |
| add | `plus-lighter`（**近似**：预乘 / 夹取口径未对账） | ✅ |
| multiply / screen | 同名 | ✅ |
| darken / lighten / overlay / soft_light / difference | 同名（`soft_light` → `soft-light`） | ❌ **还没实现**（要读目标像素，ping-pong） |

**两条规矩**（与 D8 同源，但这里的差额方向是反的）：

1. **画得出来就画** —— 不要因为引擎没有就不画；预览的价值正在于「先看见」。
2. **差额必须报出来** —— `web/dom-css.mjs` 的 `ENGINE_IMPLEMENTED_BLENDS` 一旦与
   `layer.rs` 的 `is_implemented` 不一致，判据就红。引擎哪天补上一条，DOM 侧那句「引擎还没实现」
   立刻变成**假消息**，而假消息比不报更坏：它会让人为一条根本不缺的能力去改工程。

**判据**（`scripts/check-dom-css.mjs`，已登记）：

- 混合模式用例：8 条逐值交给 CSS；`add` 必须 `APPROXIMATE` 且理由非占位；五条引擎未实现的必须报 `missing`；
- **跨文件比对**：读 `crates/dhampir-timeline/src/layer.rs` 的 `matches!(self, Self::…)`，与清单逐名对上；
- 宿主接线：第三层（`blend: darken`）的 `mix-blend-mode` 必须是 `darken`，且「引擎还没实现」要出现在回报里；
- self-test 从 2 个错误映射器涨到 **3 个**（新增「add 被当成合法的 CSS 取值」—— CSS 里根本没有 `add`，
  写了会被整条忽略）。

**还没做的**：`isolation: isolate` 只在页面 `#stage` 上设了（DOM 侧的合成范围正确）；
引擎侧的 ping-pong 基建仍未动，所以那五条**出片会拒绝整帧**（`render/compose.rs` 的整帧检查）。

## D10 几何型原语：先落设计，再动渲染主路径

**为什么单独一节**：圆角 / `clip-path` / `mask` 属于「给底座加原语」，而本仓对**渲染主路径**的改动有硬规矩：
**先落文档再写代码**（T4.0 的先例），且每一版都要过两条判据 —— ① 有像素的地方**逐字节不变**；
② 老用例**一字不改继续绿**。

**先把账分清楚：两类基建，不是一笔**

| 档位 | 现在有什么在等它 | 要加什么 | 一次能带几条 |
|---|---|---|---|
| **读回型**（ping-pong） | 5 条混合模式 + `drop-shadow` + `backdrop-filter` | 中间纹理 + 读目标像素的合成回路 | 一批（同一套基建） |
| **几何型**（geometry） | 圆角 + `clip-path` + `mask` | 每像素一个**覆盖度**（SDF 或掩码纹理） | 一批（同一套基建） |
| 其他 | Lottie | 一整套矢量渲染器 | 单列 |

（这三档写在登记表的 `needs_legend` 里，每条 `needs-primitive` 都必须标明档位 —— 判据会红。）

**几何型里先做圆角**，理由是它**最便宜且能自证**：

1. **不需要新基建**：圆角就是「每像素一个覆盖度」，在合成着色器里算个 SDF 就够 —— 不用中间纹理，也不用读目标像素；
2. **契约改动是加法**：`Layer` 上加一个可选半径（缺省 0 = 老行为），`project_schema` **不升**；
3. **判据强**：半径 0 时出片**逐字节不变**（digest 比 SHA256）；半径 > 0 时**四角应当被清掉、中心不变**（拿 Pillow 读像素）。

**无分支约束**（`plan/wgsl-portable-subset.md`）：覆盖度不能写成 `if`。圆角矩形的 SDF 本来就是无分支的：

```text
p = 该像素在图层局部坐标里的位置（相对中心）
d = length(max(abs(p) - (half_size - r), 0)) - r
coverage = 1 - smoothstep(-edge, edge, d)      // edge ≈ 半个像素，做一点抗锯齿
alpha *= coverage
```

`length` / `max` / `clamp` / `smoothstep` 都在允许表里 —— 但**动手前要用 `dhampir-wgsl-census.mjs` 普查确认**，
别假设。

**三条判据**（做的时候照着验）：

1. **半径 = 0 ⇒ 逐字节不变**：拿改动前的 digest 做基线，同参数出片比 SHA256；
2. **半径 > 0 ⇒ 角被清掉、心不变**：Pillow 读四角与中心；
3. **两端一致**：DOM 侧用 `border-radius`，与引擎的 SDF 在容差内一致（**抗锯齿不会逐像素相同** —— 容差写进容差表，别改通过线）。

**顺序不能反**：**契约字段 → 引擎实现 → DOM 侧接上**。不要在契约还没有这个字段时偷偷在 DOM 侧用 `border-radius` ——
那等于预览画了工程里没写的东西，比画不出来更坏。

### 落地进度（第 12 轮）

| 步骤 | 状态 | 判据 / 读数 |
|---|---|---|
| ① 契约字段 | ✅ | `Layer.corner_radius`（缺省 0、为 0 **不写进文件**）；单测 `圆角为_0_时不算未实现也不写进文件` |
| ② 校验层可见 | ✅ | `probe` 对半径 24 的工程给 `ok: true` + 警告 `unimplemented_corner_radius`（不阻断，但作者看得见） |

后者能证明「半径 0 时新代码路径没被走到」，但它**不等于**改动前的基线。下一次动渲染路径要先记基线。

## D12 掩码纹理：三层决定与一条不许含糊的坐标口径

**做什么**：让一层可以被**另一张图**按 alpha 或亮度裁切。它是「矢量 / 位图遮罩」整条线的起点，
**也是 `polygon()` / `path()` 不必永远"明确不做"的前提** —— 多边形遮罩可以先栅格化成掩码纹理。

**三层决定**（写下来，因为它们互相约束）：

1. **素材层**：掩码是一张**素材**（`assets` 里的一条），所以契约是「层引用素材 id」而不是「层内嵌一张图」。
   理由：素材的注册、时间基、URI 解析、"引用不存在的素材要报错"这套校验**都已经有了**；内嵌等于把它们重做一遍。
2. **采样层**：走 `textureLoad` + 自己写双线性（与合成源同一条纪律）—— **不用采样器**，
   滤波精度不许留给实现。

   > **实现时发现的一处修正（第 21 轮）**：原本写的是"越界用 `fract` 环绕（CSS 的 `mask-repeat: repeat` 与之同向）"。
   > 真写的时候才看清：v1 是**拉伸填满**，归一化坐标**永远在 [0,1] 里**，环绕根本触发不到 ——
   > 需要钳的是**双线性那四个抽头**在掩码边缘处的越界（钳到边缘，与源纹理那份写法相同）。
   > 所以 `fract` 没被用到，`mask-repeat` 不是"没做"，而是**由构造本身不可达**（要做它得先有 size/position）。
3. **坐标层**（最容易含糊，必须钉死）：掩码图的**整张**映射到**图层自己的矩形**上（拉伸填满），
   也就是说掩码用的是**图层局部坐标** —— 与合成源的"源像素坐标"**不是同一套**。
   这是本设计里唯一一处新坐标口径，判据要专门钉它：拿一张 2×2 的掩码图铺在 32×32 的层上，
   看四个象限各自的 alpha，**每个象限都要对**。

**三档不做**（明说，不留给猜）：

- `mask-size` / `mask-position` / `mask-repeat` 的自由组合：v1 只有「拉伸填满 + 环绕或钳边」；
- **渐变遮罩**：CSS 的 `linear-gradient()` / `radial-gradient()` 是**生成**一张图，不是一张素材 ——
  要做得先有"程序化生成纹理"那一层，不在这一版；
- 颜色空间转换：v1 只认 **alpha** 与 **亮度（Rec.709）** 两种通道，且把系数写进契约文档（D6 的老规矩）。

**成本与顺序**（照 D10 的老样子：先落文档，再动渲染主路径）：

1. **契约**：`Layer.mask: Option<MaskSpec>`（素材 id + 通道 + 是否反相；缺省不写进文件）；
2. **校验**（这一步**现在就能写、也就能判**）：引用不存在的素材 → **报错**；能力查询 `unimplemented_masks`；
3. **引擎**：bind group 多一个纹理 + 片元里一次 `textureLoad` 与 `fract`；`SourceResolver` 多解析一份静态图；
4. **DOM 侧**：`mask-image: url(<素材 uri>)` —— 但要说清：DOM 宿主这一版**不做素材解码**，
   所以它只是把 CSS 写上去并把"这条没实测"报出来（与 D8/D9 的"缺口要报出去"同一条规矩）。

**判据**（D10 那三条的老样子）：**没有掩码时出片逐字节不变**（基线 `8b7d9e18a7320ee7`）；
2×2 掩码铺在 32×32 上四个象限各自对，**反相后正好反过来**；两端边缘抗锯齿差异进 `geometry.edge_antialias` 那条台账。

## D13 读回型基建（ping-pong）：一次投入，三批能力

**它是什么**：一对中间纹理 + 一趟能**读目标像素**的合成回路。固定混合方程表达不了 `f(src, dst)`，
因为它们要在同一个片元里同时知道来源与目标。

**一次能带三批**（这就是它值得先做的理由）：

| 等它的能力 | 为什么它要读目标 |
|---|---|
| `darken` / `lighten` / `overlay` / `soft_light` / `difference` | 定义式就是 `f(src, dst)`，逐通道比大小或混合 |
| ~~`drop-shadow`~~ | **第 27 轮修正：它不在这一批里** —— 见下 |
| `backdrop-filter` | 要读**下面已经画好的内容**再对它跑一遍特效 |

**成本**：中间纹理（分段渲染已经有这套基建了 —— 调整图层走的就是它）+ 每段多一趟 pass；
纹理尺寸、采样纪律、坐标口径都可以沿用现有的那套，所以**这是三批里最便宜的一笔**。

**不做**：**绝不把像素读回 CPU**（那是另一件事：会引入"两端都可能读到不同的浮点结果"与同步开销）。
ping-pong 全程留在 GPU 上。

**判据**：① 现有四条已实现的模式**逐字节不变**（它们不该改走新回路）；
② 每条新模式一个 GPU 参考用例（红底叠蓝，逐点比一张写死的期望表）；
③ 能力清单与 `layer.rs` 的 `is_implemented` **跨文件一致**（这条判据已经存在 —— `check-dom-css` 在盯）。

**顺序**：排在掩码纹理之后 —— 掩码只多一张**输入**纹理，ping-pong 改的是**回路**，后者风险更大。

### 第 30 轮：落地方式定下来了（**复用分段渲染**，不另建一对）

读完 `render_segmented` 才敢定：它已经维护着一个 `current: Option<usize>`（"当前底是哪张纹理"），
而且有现成的搬运惯例（`PairSource` / `FixedSource` / 最后落回 target 那一步）。所以读回型**不必**重写合成回路：

1. `Step::Draw` 已经把"底"渲染进一张纹理了 —— 读回型只要在它**之后**插一步；
2. 新增 `Step::BlendFn { layer, mode }`：`plan_steps` 对 `!uses_fixed_equation()` 的层发它，
   **并且不把它塞进 `Draw`**（否则它会被当成固定方程画一遍）；
3. `render_frame_at` 的分支从「有 `Adjust` 才走分段」改成「**有任何非 `Draw` 步就走分段**」；
4. `BlendFn` 的处理：把这一层单独渲到一张新纹理（它自己的 opacity / 掩码 / 裁剪都在里面）→
   再按 `f(src, dst)` 写回另一张 → `current` 换成它。

**这一轮真的落地的部分（谓词拆分）**：`uses_fixed_equation()` 与 `is_implemented()` 是**两件事** ——
"要读目标"不等于"做不到"。合成器建管线与 `pipeline_for` 必须用**前者**：`blend_state` 对另外 5 条返回 `None`，
而 wgpu 的 `None` 是**不混合**（= 直接覆盖目标）—— 那不是"做不到"，是**画错**。
这条极容易在"放开 `is_implemented`"的那一刻静默发生，所以先把谓词、文档与那条一致性断言都摆正。

**判据落地情况（第 31–32 轮）**：

### 第 27 轮修正：`drop-shadow` 不属于读回型

写实现方案时才看清：读回型要读的是**目标像素**（`f(src, dst)`）；而投影读的是**它自己**的邻域
（"把这层模糊一下、染成黑、挪个位置，画在它下面"）—— 而**分离式模糊早就在了**。
所以它不是 ping-pong，而是**「同一层多画一张」**，档位另记 `compose`。

**这一步的落地（第 27 轮，契约先行）**：

| 步骤 | 状态 | 说明 |
|---|---|---|
| ① 契约 | ✅ | `Layer.shadow`：`offset_x` / `offset_y` / `blur_sigma`（**CSS 的 σ 口径**，按 D5 换算 `radius = 2σ`）/ `opacity`；颜色 v1 **固定黑**（要彩色再加字段） |
| ② 取值口径 | ✅ | `σ ∈ 0..=8`（上界来自 D5：本仓核半径 ≤ 16）、`opacity ∈ 0..=1`；越界报错 —— 否则作者设 20 只会得到一个"比想要的糊得少"的投影（静默偏差） |
| ③ 可见 + 拒绝 | ✅ | `probe` 给 `unimplemented_shadow` 警告；渲染前**拒绝整帧**（求值层那一层查，占位层也拦得住） |
| ④ DOM 侧 | ⏳ | CSS `filter: drop-shadow(x y σ black)` —— 与引擎同一个语义，直接映射 |
| ⑤ 引擎「多画一张」 | ✅ **第 28 轮** | 着色器加 `tint` 开关（不染时 `select` 取原值 ⇒ **逐字节不变**）+ 准备循环里为该层多推一张（模糊后的自己 + 偏移 + 染色 + 浓淡），画在本层下面。GPU 用例四条：偏移/染色、**画在下面**（本层像素与没投影时逐字节相同）、模糊确实跑（必须用**有 alpha 边界**的源 —— 整体不透明的源做模糊是恒等变换）、浓淡减半 |
| ⑤′ 模糊向外扩散 | ✅ **第 29 轮** | 做成「**先把轮廓渲染进一张带透明留白的中间纹理，再模糊它**」：直接模糊源纹理只会向内软化 —— **模糊一个常量还是那个常量**。留白宽度 = 模糊半径（σ → `radius = 2σ`），所以扩散**有界**（半径 × scale）；形状（圆角/裁剪/掩码）**烘进轮廓**，阴影那一张不再重复裁剪（否则扩散出去那圈会被再裁一次）。判据点按几何选（本层 [8,24)²、阴影偏移 +4 ⇒ 轮廓 [12,28)²、扩散 8 像素 ⇒ 左边界到 x=4），取 (5,16) 断言"框外有颜色"、取 (2,16) 断言"扩散之外没有" |

**老工程逐字节不变**：`frame(plain)` 的 sha256 仍是 **`8b7d9e18a7320ee7`**。

## D14 矢量渲染器（Lottie / Rive）：量级不同，明确不在本轮

**它要什么**：路径（贝塞尔）→ 填充 / 描边 / 渐变 / 遮罩的栅格化器，且两个宿主都要。

**为什么它不该混进对齐工作**：前面几档都是"在同一个渲染器上多一种像素算法"，
这一档是"再写一个渲染器"。本仓的纪律（`core` 零 `#[cfg]`、两宿主共用同一份）意味着它只能落在 `core` 里
做成**纯 CPU 栅格化**（`animation.rs` 里 GIF/WebP 的"在 core 里解码"就是这个先例）——
那是另一个课题的规模，不是这一轮的。

**现在做什么**：登记表里把它标成 `needs-primitive` + `needs = other` + 指向本节，
**并且在能力声明里说清"不做"** —— 让下游现在就能据此做产品决定，而不是等一个没有日期的承诺。
